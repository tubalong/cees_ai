# 用户级记忆（User Memory）

> 状态：分块实施中——块 1-3（数据模型与契约、NestJS 记忆 CRUD、ai-service 提炼与 NestJS 合并落库）已落地，块 4-5 待实施。最后更新：2026-09-21。

## 1. 目标与边界

### 1.1 背景

当前系统没有跨会话的长期记忆能力，AI 只具备三类与"记住"相关的既有机制：

| 机制 | 记住什么 | 生效范围 |
| --- | --- | --- |
| 上下文压缩（ConversationSummary） | 单个会话内的历史摘要 | 仅本会话，不跨会话生效 |
| 用户个人资料（UserProfile） | 账号展示资料（姓名、头像等） | 全局账号信息，非对话提炼 |
| 知识库 | 团队级文档与资料 | 租户级，显式上传，非对话提炼 |

后果：用户每开一个新会话，AI 就"失忆"，需要重新介绍自己的偏好、负责的工作和过往决策。

### 1.2 目标

为 AI 助手增加**用户级长期记忆**：从对话中提炼关于用户本人的长期有效信息，跨会话持久化并在后续对话中注入，使 AI 在新会话中依然"认识"这个用户。

### 1.3 与既有机制的边界

| 机制 | 解决什么 | 例子 |
| --- | --- | --- |
| 用户级记忆（本设计） | 懂你 | "王工喜欢表格输出""王工负责华南区项目" |
| 知识库 | 懂公司 | 产品文档、团队约定、项目资料 |
| 上下文压缩 | 记得本会话聊过什么 | 本会话摘要，会话结束即不再复用 |

记忆与压缩的区别：压缩是**会话内**能力，摘要只服务于当前会话；记忆是**跨会话**能力，新会话自动继承。两者互不替代。

## 2. 范围决策：仅支持用户级，不支持租户级

> 决策：**跨会话记忆只做用户级，不做租户级**。

### 2.1 决策理由

1. **知识库已经是租户级事实源**。知识库具备双层正交权限、状态机、审核、转存链路等完整能力，团队级信息的沉淀路径已经存在，无需再造一层。
2. **租户级记忆会制造第二事实源**。租户大、用户多（一个租户下有大量成员），多人对话都在往"公司记忆"里写，会产生：互相矛盾的信息、无人负责的条目、双处管理（知识库 + 记忆）的维护负担。维护成本高于收益。
3. **知识库与用户级记忆分工互补，无功能缺口**。知识库解决"懂公司"，用户级记忆解决"懂你"，两者覆盖全部场景。

### 2.2 团队级信息的沉淀路径

对话中出现团队级共识（如"下季度主打产品 X"、"团队约定文档用 Markdown"）时，**不进入任何记忆层**，而是沿用现有链路引导用户转存进知识库（`save_to_knowledge` 工具与文档卡片的"存入知识库"按钮）。一条路走到头，不另开新路。

### 2.3 通俗类比

- 知识库 = 公司档案柜：员工主动整理、盖章归档的正式文件，权威、走流程。
- 用户级记忆 = 私人秘书的笔记本：只记关于你本人的事，只有你可见，可随时撕掉某一页。

## 3. 核心概念

### 3.1 记忆归属：绑定 membership，不绑定全局用户

记忆挂在**租户内身份（membership）**上，而不是全局用户上。理由：一个自然人可能在多个租户拥有账号，两边身份互相独立；A 租户对话中提炼的记忆绝不允许在 B 租户生效（跨租户泄漏红线）。

### 3.2 记忆类型

| 类型 | 含义 | 例子 |
| --- | --- | --- |
| PREFERENCE | 偏好 | "喜欢表格形式输出""希望回答简洁" |
| FACT | 个人事实 | "负责华南区项目""岗位是销售总监" |
| DECISION | 已做决定 | "下季度预算砍半" |
| HABIT | 工作习惯 | "每周五下午要交周报" |

### 3.3 状态

- `ACTIVE`：生效中，参与注入（默认状态，自动生效）；
- 软删除：用户删除后立即停止注入，数据保留用于审计追溯。

## 4. 功能流程

记忆链路按**代码流程层 / prompt 层 / LLM 判断层**三层分工，与项目"AI 建议权、NestJS 执行权"的既有规范一致：

| 层 | 职责 | 通俗类比 |
| --- | --- | --- |
| 代码流程层 | 何时触发、是否写入、状态流转、上限约束 | 公司规章制度 |
| prompt 层 | 规定判断规则与输出格式 | 秘书工作手册 |
| LLM 判断层 | 规则之内对具体内容做语义判断 | 秘书本人 |

### 4.1 触发时机（代码流程层）

AI 不会每句话都记，仅在以下两个时机触发记忆提炼，且均复用既有 LLM 调用，不增加额外调用次数：

- **上下文压缩时**：`ChatCompactor` 生成摘要时顺带输出记忆候选。压缩本来就要做一次 LLM 调用且语义上下文完整，零额外成本；覆盖长对话中缓慢显现的长期信息；
- **用户明确表达倾向时**：用户在某轮对话中明确表达偏好、事实、决定或习惯（如"以后都…""我希望…""记住…""我负责…"）时，随该轮回答一次输出记忆候选，复用 related_questions 的"随回答输出 + 流式剥离"链路（`FollowUpStreamFilter` 同模式），及时且零额外调用；仅最终回答轮生效，工具调用轮次不输出记忆候选。

### 4.2 提取与筛选（prompt 层规定规则，LLM 层执行判断）

prompt 规定"什么算值得记"，LLM 拿规则在具体对话上判断：

1. **长期有用**：随口问天气不记；"以后给我报价都用表格"才记；
2. **关于用户本人**：只提炼用户的偏好、事实、决定、习惯（见 3.2 四类），团队级信息不提炼（见 2.2）；
3. **尚未记过**：已存在的条目不重复提炼；
4. **只引用用户原话**：不脑补、不推断，每条候选必须能在对话原文中找到依据；
5. **敏感内容过滤**：密码、证件号、薪资等敏感信息不提炼；prompt 先约束，代码层再兜底检查一遍。

### 4.3 合并（LLM 判断 + 代码执行）

提炼出的候选与已有记忆对比，LLM 只输出合并建议，NestJS 执行写入：

| 场景 | 处理 |
| --- | --- |
| 新主题 | 新增一条 |
| 同一主题有新信息 | 覆盖旧条目（版本递增） |
| 新旧矛盾 | 以用户最新表述为准，覆盖旧条目 |

LLM 只出"新增/覆盖/丢弃"的建议，真正改库由 NestJS 完成，符合"模型建议权、NestJS 审批执行权"规范。

块 3 落地要点（已实现）：

- ai-service 在两个时机输出 `memory_candidates`（内部契约 `UserMemoryCandidate`：`type` / `content` / `action=create|update` / `replaces`）：压缩响应的 `CompactChatResponse.memory_candidates`，以及最终回答轮 completed 事件的 `ChatStreamCompletedEvent.memory_candidates`；随回答链路复用 `<follow_up_questions>` 块的对象格式（`questions` + `memories` 字段，兼容旧数组格式），仅最终回答轮生效，工具调用轮次不输出；
- NestJS `UserMemoryService.applyCandidates` 统一校验（类型、长度、敏感正则兜底、update 必须携带 `replaces`）后在事务内合并：`replaces` 命中旧记忆原文片段则覆盖（乐观锁版本递增），未命中降级新增，完全重复跳过；达到 30 条上限淘汰最久未使用条目；
- 每次写入均记录审计事件（`USER_MEMORY_CREATED` / `USER_MEMORY_UPDATED` / `USER_MEMORY_EVICTED`，来源 `ai_suggestion`），落库失败只记录日志，不影响本轮回答与压缩。

### 4.4 可控性（代码流程层）

- **自动生效 + 透明可见**：记忆提炼后自动进入 `ACTIVE`，同时在"我的记忆"面板完整列出，用户可查看、修改、删除任意条目。删除立即停止注入。
- 不做"每次提炼前弹窗确认"（高频打断体验差），以"事后可见可删"兜底。
- 记忆的写入、修改、删除均记录审计事件（操作者、条目、来源会话/轮次）。

### 4.5 防乱写（代码 + prompt 混合）

- **数量封顶**（代码强制）：每人记忆条目上限 **30 条**，达到上限后淘汰最久未使用条目；
- **脱敏**（prompt + 代码兜底）：见 4.2 第 5 点；
- **只记说过的**（prompt 规定）：见 4.2 第 4 点。

## 5. 数据模型（块 1 已落地）

NestJS 事实源已通过 Prisma 迁移 `20260921021045_add_user_memory` 落地，最终模型：

```prisma
enum MemoryType {
  PREFERENCE
  FACT
  DECISION
  HABIT
}

model UserMemory {
  id                   String     @id @default(uuid()) @db.Uuid
  tenantId             String     @map("tenant_id") @db.Uuid
  /// 归属成员身份而非全局用户：同一自然人在不同租户的记忆互相隔离。
  membershipId         String     @map("membership_id") @db.Uuid
  type                 MemoryType
  content              String     @db.Text
  sourceConversationId String?    @map("source_conversation_id") @db.Uuid
  sourceTurnId         String?    @map("source_turn_id") @db.Uuid
  createdAt            DateTime   @default(now()) @map("created_at")
  updatedAt            DateTime   @updatedAt @map("updated_at")
  deletedAt            DateTime?  @map("deleted_at")
  version              Int        @default(1)

  @@index([tenantId, membershipId, deletedAt])
  @@map("user_memories")
}
```

要点：

- 无向量字段：用户级记忆每人 30 条封顶，全量注入，无需向量检索；
- 同一 subject 通过"相同主题覆盖"收敛为一条，避免同主题多条目并存；
- `membershipId` 为纯标量无 relation（与 `Conversation.ownerMembershipId` 风格一致），归属校验由应用层结合租户上下文完成。

## 6. 注入

- 方式：**全量注入**。每次组装上下文时，将该用户该租户的全部 `ACTIVE` 记忆作为独立 system 块注入（如"以下是关于你的长期记忆：…"）。
- 位置：与 `conversation_summary` 分开，语义不同——摘要=本会话历史，记忆=跨会话长期事实。
- 契约：`ChatRequest` / `ToolTurnRequest` 已新增 `user_memories` 字段（`type: [array, "null"]`，至多 30 条、每条至多 1000 字符，缺省/null 表示不注入），Python models 与 TS 客户端已重新生成（块 1 落地）。
- 冲突处理：用户级记忆与知识库检索结果冲突时，**以记忆为准**（记忆是用户本人最新表述）。

按项目"大型功能分块渐进实施"约定，每块独立可验证、独立提交，全部完成后一个 PR：

3. **ai-service 提炼**（块 3，已完成）：压缩时顺带输出记忆候选 + 用户明确倾向时随回答输出（复用 related_questions 链路），NestJS 合并落库（见 4.3 落地要点）；

5. **桌面端面板**：对话页"我的记忆"入口、列表、编辑/删除交互。

# AI 同事：定位与关系说明

> 状态：设计定稿（2026-09-28）
> 性质：概念与边界定义文档。本文档定义的主体、归属与边界是任务编排设计的前提；修改其中任何边界，需要同步核对 [AI 任务编排（需求设计）](ai-orchestration.md) 与 [AI 任务编排技术设计](../architecture/ai-orchestration-technical.md)。
> 读者：产品、设计、桌面端 / 移动端、服务端、测试。

## 1. 为什么需要本文档

「AI 同事」如果只按"带人设的聊天机器人"理解，会连续引发四类系统性设计错误：

| 错误理解 | 直接后果 |
| --- | --- |
| 当作普通私聊工具，权限随会话、经验留在聊天记录 | 要么越权（同事以用户身份干了超出职能的事），要么无法积累（同事没有独立权限位，经验不沉淀） |
| 当作"需要装知识库的实体"，为其复制企业文档 | 企业事实出现多份副本，权限模型翻倍，同步链路永远追不上"最新企业动作"，版本必然漂移 |
| 当作"个人助手"，把工作经验记入个人记忆 | 多人共用同一同事时，经验无法沉淀、互相覆盖；同事能力永远不进化 |
| 当作"黑盒执行者"，不记录代表谁、消耗谁的额度 | 行为无法归因、无法审计、无法计费，安全与合规同时失控 |

本文档先定义四个主体（第 3 节）与它们的关系（第 4 节），再给出 AI 同事的能力构成（第 5 节）与安全边界（第 7 节）、并发一致性原则（第 8 节）。编排、权限、记忆、审计相关设计均以本文档为准。

## 2. 背景：任务为什么要交给"同事"

### 2.1 产品方向

平台的方向是：AI 助手成为平台唯一操作入口，用户在单一对话界面中完成全平台操作——默认与总管交流，也可以从同事入口（同事页、档案页）进入与某位同事的会话；复杂请求可以在对话内展开为多步骤任务编排；不同职位看到与职责匹配的内容；AI 能够主动发现与推动（"事找人"而非"人找事"）。

当用户请求从"一问一答"升级为"完成一件事"（例如：生成本周经营简报、制作演示视频、发起一轮合同审查），单个对话助手在三处到达边界：

- **专业分工**：不同步骤需要不同的工具面、指令与判断标准；
- **上下文容量**：一个任务的全部中间过程塞进单一会话窗口，会污染主线对话并推高成本；
- **权限与并行**：不同步骤的风险级别不同，应当分别授权、分别审计，部分步骤还可以并行。

### 2.2 现状约束（代码层面的事实）

- 对话运行器按"一问一答 + 工具循环"设计（单轮工具调用有明确轮次上限），没有"长时间运行的任务"这一概念；
- 上下文压缩与用户级记忆面向单会话、单用户模型；
- 工具调用由服务端统一程序化批准（权限、额度、幂等、参数校验），模型只有建议权、没有执行权；
- 不存在任务、计划、子执行等数据模型，也没有可被复用的"执行单元"实体。

结论：需要把"执行一件事"的能力从单体对话循环中剥离出来，形成**总管调度 + 同事执行**的分工结构。

### 2.3 行业模式选择：为什么是主管-工人

主流多 Agent 协作模式有四种：Supervisor（主管-工人）、Handoff（移交）、GroupChat（群体讨论）、Graph（图编排）。本项目选择**主管-工人**，理由如下：

1. **与服务端唯一编排中心的既有架构一致**。平台已经确立"NestJS 是唯一编排中心、模型只有建议权"的原则，主管-工人是该原则在多 Agent 场景下的自然延伸：总管负责生成计划，代码负责驱动状态机，同事只负责在各自窗口内执行步骤。
2. **失败可局部恢复**。某一步失败只需要重试或重排该步骤，不影响其他已完成步骤；GroupChat 模式下任意一条消息都可能影响全局，失败定位与恢复代价高。
3. **成本与上下文可控**。每个同事只在独立窗口里加载"派发书 + 依赖产出 + 必要记忆"，不携带全量会话历史。行业实践显示多 Agent 系统的 token 消耗可达单 Agent 的十几倍，如果不做窗口隔离与摘要回流，成本会先于功能失控。
4. **权限可收窄**。同事的权限是"发起人权限 ∩ 同事权限上限"，天然可推导、可审计。

**被拒绝的方案**：

- **GroupChat**：消息广播导致上下文互相污染、权限难以收窄、成本不可预测，且与本项目"结构化状态、代码驱动"的哲学相悖；
- **Handoff（全权移交）**：把控制权整体交给某个子 Agent，等于放弃服务端对状态机与审计的掌握，与"程序化批准"的既有约束冲突；
- **纯 Graph 预编排**：任务计划在开工前完全固化，无法应对执行中的意外（步骤失败、产出不达标、用户插话），而动态重编排正是本项目的核心需求。

## 3. 四个主体

### 3.1 企业（租户）——资产所有者与事实源

- **定义**：使用平台的法人组织，即系统内的租户。
- **拥有**：企业知识库（企业知识的事实源）、AI 同事（含其职能定义、工作记录、学习记录）、任务产生的产出与记录。
- **边界**：AI 同事的一切配置、行为记录、经验沉淀归企业所有，不随创建人或使用人转移。

**为什么**：企业是唯一能对"同事能力"负责的主体。职能定义、权限上限、经验准则都必须由企业（或企业授权的管理员）维护，才能保证同事在多用户共用下行为一致。

### 3.2 用户（成员）——员工

- **定义**：企业中的自然人成员（系统内的 Membership）。
- **拥有**：账号与角色权限、个人资料、**用户级记忆**（跨会话的个人偏好与事实）。
- **边界**：用户级记忆归个人，不会因为其使用某个同事而进入企业资产；成员离职或停用采用软删除，历史记录中对该成员的引用保持有效。

**为什么**：个人偏好（如"回答先给结论"）属于个人隐私与个体习惯，与"企业希望同事怎么干活"是两个维度，混在一起会导致同事在多人共用时行为互相覆盖。

### 3.3 主对话 AI（总管）——用户的私人代理

- **定义**：用户与平台对话时的主 AI 角色。职责只有三件事：**理解意图、生成计划、汇总答复**。
- **归属**：会话私有（归属于发起用户），不属于企业资产。
- **能力**：拥有用户可用的全部工具（受用户权限约束）、用户级记忆、主会话上下文（含压缩摘要）。
- **边界**：总管不亲自执行长任务的重活（交给同事）；总管会话内容不进入企业知识库；总管可以代表用户发起任务、审批授权、回答问题，但不能代替企业管理员修改同事配置。

**为什么**：用户需要一个"只对我负责"的代理来承载私人会话（隐私边界），同时企业需要可复用的执行单元来承载任务（资产边界）。两者的归属不同，必须分成两个实体。总管选择"理解意图、生成计划、汇总答复"三个职责，是因为这三件事都需要主会话的私人上下文；而中间的执行过程不需要，且不应污染主会话。

### 3.4 AI 同事——可对话、可调度的企业能力单元

- **定义**：由企业创建、具有职能定义、权限边界与经验积累的 AI 执行单元。用户既可以直接与同事对话（前台对话），也可以由编排把任务步骤交给同事执行（被调度执行）。
- **归属**：企业资产。职能定义（AgentDefinition）、工作记录、学习记录均归企业。
- **调度**：任何有权限的用户都可以调度任一同事或与其对话，同一同事可被多人、多任务同时使用。

**两种运行模式**：

| | 前台对话（用户 ↔ 同事） | 被调度执行（编排中的执行者） |
| --- | --- | --- |
| 触发 | 用户从同事入口进入与某位同事的会话 | 总管生成任务计划后，由服务端按步骤派发 |
| 会话 | 有：按"用户 × 同事"组织的会话，可回看、可继续 | 无：执行窗口随步骤生灭，以派发书为上下文 |
| 上下文 | 职能定义 + 学习记录 + 工作记录摘要 + 本会话流 + 工具与知识库检索 +（发起人自己的）用户级记忆 | 派发书 + 依赖产出 + 相关记忆 |
| 权限 | 发起人权限 ∩ 同事权限上限（含三级边界，见第 7 节） | 同左，按步骤逐项校验 |
| 会话与记录 | 会话归发起用户：默认仅本人可见、企业审计可查；对话原文不移交企业侧，沉淀到同事侧的是工作记录摘要与经验条目 | 无会话；全过程记录在任务状态与审计中 |

- **边界**：
  - 不是任何用户的私人助理：同事不随创建人转移，任何有权限的用户都可以与其对话或调度它；
  - 同事之间的协作没有会话：多同事协作通过任务状态与产出传递，不通过"同事间聊天"；
  - 被调度执行时不携带私人会话内容：执行窗口只接收派发书与依赖产出，不直读用户私人记忆；
  - 不能超越权限上限：即使发起人权限更高，同事也只能在其职能上限内行动（见第 7 节）。

**为什么这样定义**：三个目标同时成立——用户即取即用（可直接对话咨询，也可交给编排办长任务，不必关心同事内部细节）、企业统一治理（配置、审计、经验沉淀）、系统安全并发（会话隔离、执行窗口隔离，资产只读共享）。注意："同事没有私人会话"仅指上述边界（不是私人资产、协作无会话、执行不带私人会话内容），不代表用户不能与同事对话。

## 4. 关系模型

```
企业（租户）—— 资产所有者、事实源
 ├── 企业知识库（共享读，权限过滤）
 └── AI 同事（资产）
       ├── 职能定义（AgentDefinition）
       ├── 学习记录（程序性知识，影响行为）
       ├── 工作记录（情景记忆，append-only）
       └── 权限上限（三级：自决 / 需签字 / 禁止）

用户（成员）—— 员工
 ├── 用户级记忆（私人）
 ├── 与总管的会话（私人）
 └── 与同事的会话（用户 × 同事，默认本人可见）

两条通往同事的通道：
 ① 前台对话：用户 ──对话──▶ 同事                        咨询、追问、委托简单事项
 ② 编排执行：用户 ──发起任务──▶ 总管 ──计划 / 派发──▶ 同事   多步骤任务协作

任务 = 企业行为：由总管编排、同事执行，记录与产出归企业
```

两条清晰的归属线：

| 维度 | 私人线 | 企业线 |
| --- | --- | --- |
| 主体 | 用户 → 总管 | 企业 → AI 同事 / 知识库 |
| 数据 | 会话（与总管、与同事）、用户级记忆 | 职能定义、工作记录、学习记录、产出 |
| 可见性 | 仅用户本人 | 企业内按权限可见 |
| 生命周期 | 随用户 | 随企业 |

两条线的**交汇点是任务**：用户通过总管发起任务，任务调度企业同事执行，任务的记录与产出归企业。前台对话（通道①）不产生任务；对话中升级的复杂请求转为任务（通道②），两条通道共享同一套同事资产与权限模型。

**为什么这样切**：三个理由——（1）**知识闭合**：企业事实只有一个事实源，不存在"某个同事知道而企业不知道"的信息；（2）**权限可推导**：任何一次操作的授权来源是"发起人 + 同事上限"的交集，可机械化校验；（3）**可归因**：每个任务都能回答"谁发起的、哪个同事干的、消耗了谁的额度、留下了什么记录"。

## 5. AI 同事的能力构成

AI 同事由五个部分构成。前三者是"行为"（怎么想、怎么学、做过什么），后两者是"边界"（能看什么、能干到什么程度）。

### 5.1 职能定义（AgentDefinition）——岗位说明书

内容包括：名称、职能描述、执行指令（工作方式、输出标准）、可用工具清单、权限上限、风险级别、可见性（哪些角色可调度）。

**为什么**：同事的行为需要可配置、可评审、可版本化。将"岗位说明书"独立于执行过程存储，才能实现"改配置立即生效于下一次执行、执行历史不受影响"。这也是"创建 AI 同事"流程的数据基础。

### 5.2 数据源挂载——对企业知识的访问方式

同事不拥有独立的文档知识库。它对企业和业务信息的访问通过**挂载**实现：

| 挂载对象 | 访问方式 | 说明 |
| --- | --- | --- |
| 企业知识库 | 检索工具（RAG） | 与创建同事时的"数据源勾选"对应；权限过滤后检索 |
| 业务系统（CRM / 财务 / HR / 会议等） | 工具实时查询 | 不灌入上下文、不复制进知识库 |
| 连接器（GitHub、钉钉等） | 对应远程工具 | 授权按发起用户维度持有 |

**为什么不为同事复制独立知识库**：

1. **同步不可靠**：需求明确要求"同事的信息永远是同步的最新企业动作"。物理复制必然产生落后副本，而不复制、执行时实时读取，天然就是最新；
2. **权限模型翻倍**：企业知识库已有一套权限体系，独立副本意味着两套权限要保持一致，任何一次疏漏都是越权口子；
3. **碎片化**：同一份文档出现在多个同事的知识库里，版本、删除、审计全部失控。

"同事专属资料"的正确做法是**挂载引用**：在企业知识库中给文档挂上"适用同事 / 职能"的标签，同事检索时默认加权或限定标签——书还是那些书，标签只是"推荐书架"。

### 5.3 学习记录——程序性知识（"怎么干活"的经验）

学习记录是同事在执行与协作中沉淀的**经验条目**，直接调整其行为，示例（按来源分类）：

| 来源 | 示例 |
| --- | --- |
| 用户反馈 | "反馈：'简报 3 忧太多' · 已调整正负比例" |
| 行为模式 | "该用户多次询问某客户情况 · 已加入重点跟踪列表" |
| 自主复盘 | "基于最近 20 次阅读行为 · 已优化简报开头方式" |
| 错误纠正 | "曾混淆'高风险'与'高优先级' · 已修正判断逻辑" |
| 外部知识 | "新规已将某类用语列为违禁 · 已加入词库" |

学习记录与用户级记忆的边界：

| | 用户级记忆 | 学习记录 |
| --- | --- | --- |
| 归属 | 用户个人 | 同事（企业资产） |
| 内容 | 关于用户的偏好与事实 | 关于工作方式与准则 |
| 示例 | "先给结论再给依据"（该用户的偏好） | "输出结构：先结论后依据"（同事的准则） |
| 共用影响 | 仅对该用户生效 | 按适用范围对相关执行生效 |

**设计要点**：

1. **所有对人的引用使用成员实体 ID（membershipId），不存储姓名字符串**。成员离职、换岗、改名后，历史记录仍然指向同一个实体，展示层实时解析当前姓名与职位，不会出现"数据里到处是名字、人一走全乱套"的情况；需要还原历史时刻的场合（审计）由审计事件附带操作时刻快照解决。
2. **每条学习记录带适用范围（scope）**：全局准则 / 特定用户条件 / 特定场景。两位领导对输出格式提出不同要求时，按 scope 分流（对该用户按 A 格式，对其他用户按 B 格式），而不是互相覆盖。
3. **提取与生效规则**：反馈类默认仅对反馈者生效；自主复盘类默认全局生效；高影响的行为变更可配置为需职能负责人确认后生效。
4. **注入方式**：同事每次执行时，按"相关性 + 适用范围"过滤后注入执行上下文——现查现注入，读取的永远是最新版本。
5. **append-only**：学习记录只追加、不原地修改；被新经验取代的旧条目标记失效而非删除，保留完整演化轨迹（同事档案中"学习进度"对应的就是该记录集）。
6. **生成来源**：任务执行复盘（自主复盘、错误纠正）与前台对话沉淀（用户反馈、行为模式）均可产生学习记录候选；进入企业侧的是经验条目本身，产生它的私人对话原文不移交（与 3.4 节会话边界一致）。

**为什么必须"属于同事自己"**：文档知识是企业共享的（谁都能读同一份制度），但经验是执行个体的能力，无法共享——财务同事的行文经验对研发同事无意义。物理复制文档是错误，经验沉淀不归己同样是错误，两者是"共享事实"与"个体能力"的分野。

### 5.4 工作记录——情景记忆（"做过什么"）

内容是每次执行的摘要：任务或前台对话、发起人（成员 ID 引用）、时间、涉及步骤或话题、产出引用、结果与复盘要点。append-only，归企业。前台对话进入工作记录的是摘要级条目，对话原文留在用户侧会话中。

**为什么**：三个用途——（1）档案展示（对应原型中"今日做的"区块）；（2）执行时注入"最近做过什么"，保证工作连续性；（3）审计与绩效统计的事实来源。

### 5.5 权限边界——三级授权（详见第 7 节）

同事的权限清单按"自决 / 需签字 / 禁止"三级表达（与原型一致），例如："读取业务数据 = 自决；对外发送 = 需签字；最终资金与人事决定 = 禁止"。

## 6. 边界：AI 同事是什么、不是什么

| 是 | 不是 |
| --- | --- |
| 企业创建、企业所有的虚拟员工 | 某个用户的私人助理（不随创建人转移、不服务单一个人） |
| 可对话、可调度的执行单元（前台对话 + 编排执行两种模式） | 会"聊闲天"的娱乐型聊天机器人（对话目的始终是工作） |
| 职能 + 经验 + 权限的载体 | 企业知识库的副本（知识通过挂载共享） |
| 工作记录与学习记录的归属主体 | 用户记忆的替代品（记忆归用户本人；前台对话仅引用发起人自己的记忆，执行模式只接收派发书上下文） |
| 权限受"发起人 ∩ 上限"双重约束的执行者 | 可自行扩大权限、自行执行对外动作的自由体 |

## 7. 权限与授权

### 7.1 权限推导公式

```
同事某次执行或对话的可用权限 = 发起人权限 ∩ 同事权限上限
```

两个方向都不放开：发起人再高（如 CEO），同事也不能超出其职能上限（如"禁止代表公司签约"）；同事上限再宽，发起人没有的权限也不能借道执行（如实习生发起，不能因同事有导出权限就允许导出）。前台对话与任务执行使用同一公式，不因"只是聊天"而放宽数据与工具范围。

**为什么**：这是安全红线。若无"∩ 上限"，同事成为权限放大器（借同事越权）；若无"∩ 发起人"，同事成为绕过人审的通道。两者叠加才能保证"AI 不越权"的系统级约束在执行单元上同样成立。

### 7.2 三类权限状态与三个动作体系

| 权限状态 | 含义 | 执行时的动作 |
| --- | --- | --- |
| 自决 | 职能内常规操作 | 直接执行，全程审计 |
| 需签字 | 高风险或对外动作 | 暂停步骤，向发起用户推授权卡片；批准后继续 |
| 禁止 | 不可逾越的边界 | 直接拒绝；模型转向替代方案 |

与既有机制的衔接：工具调用仍由服务端程序化批准（权限、额度、幂等、参数），"需签字"本质是在批准流程中插入"人工确认"节点；每次写入类操作仍保留写操作确认（待确认草稿）机制，与授权叠加构成双层保护。

### 7.3 临时授权

当同事执行到权限不足的步骤时（典型场景：任务最后一步需要对外发送、员工临时需要一项超出同事职能上限但自己有权做的操作、连接器未完成授权），允许发起**临时授权申请**：

1. 步骤挂起（不阻塞无依赖的其他步骤），主会话流推送授权卡片：谁、要什么、为什么、影响范围；
2. 用户选择"仅本次 / 本任务内允许"，或拒绝；
3. 批准后临时生效；**仅在该任务执行期间有效，任务终态（完成 / 失败 / 取消）即失效**；
4. 申请、决定、使用全量记录并进入审计。

**为什么两条硬约束是必须的**：（1）任务期失效——临时授权的语义是"为了让这个任务完成的一次性豁免"，脱离任务的长期授权会让"临时"变永久，权限边界形同虚设；（2）全量记录——授权是安全事件的最高敏感级，必须可回答"谁在什么时候批了什么、被用在了哪里"。

## 8. 多人共用与一致性原则

同一同事会被多名用户、多个任务同时调用。系统基于三条原则保证一致性，而不是靠加锁或复杂同步：

1. **实例隔离**：每次执行是独立的执行窗口（派发书 + 依赖产出 + 相关记忆），"人群职能"只读共享。多个任务调用同一同事 = 多实例并行，互不干扰。
2. **读取时最新**：同事"永远同步最新企业动作"的实现方式是——不维护脑中缓存，每次执行时从事实源（企业知识库、工作记录、业务工具）现查现注入。因此"完成先后顺序"问题自然消解：后启动的执行读到的一定包含先完成者的结果。
3. **追加写入**：工作记录、学习记录、知识产出均为 append-only；任务之间数据隔离。共享状态里没有"原地覆盖"的冲突点，因此不需要分布式锁。

对"同一属性的活被并发执行"（如两位用户同时要一份经营简报）：并行产出各自资产是合法行为；编排层可选做"近期相关产出检测"，提示复用已有产出——这是效率优化，不是一致性要求。

## 9. 与既有概念的关系

| 既有概念 | 与 AI 同事的关系 | 防混淆说明 |
| --- | --- | --- |
| 用户级记忆 | 相互独立；同事不直读 | 记忆归属用户，学习记录归属同事 |
| 企业知识库 | 同事以"挂载 + 检索"方式访问 | 不复制、不建副本 |
| AI 管家（主动提醒） | 不同职责：管家负责"事找人"的主动提醒与跟进闭环 | "管家"专指主动提醒模块；本文档的"总管/同事"专指任务编排体系，两者术语不得混用 |
| 连接器（钉钉、GitHub 等） | 同事数据源的接入通道；授权按发起用户持有 | 工具发现与执行沿用既有连接器运行时 |
| 对话轮次（Turn） | 用户与总管、或用户与同事的一问一答单元；任务是跨轮次的长期存在 | 任务不等于一轮对话，也不寄生在某一轮上；前台对话与编排执行是两条通道 |
| 写操作确认 | "需签字"与写入确认叠加为双层保护 | 授权解决"有没有资格"，确认解决"这一次要不要执行" |

## 10. 术语表

| 术语 | 定义 |
| --- | --- |
| 企业（租户） | 使用平台的法人组织；同事与知识资产的归属主体 |
| 用户（成员） | 企业内的自然人；发起任务的授权来源 |
| 总管（Supervisor） | 对话中的主 AI 角色；理解意图、生成计划、汇总答复 |
| AI 同事（Worker） | 企业创建的、可对话、可调度的执行单元 |
| 任务（Task） | 用户通过总管发起、由计划与步骤构成的、跨轮次存在的执行单元 |
| 步骤（Step） | 任务的最小调度单位；一个步骤由一位同事在一次独立执行中完成 |
| 派发书 | 编排器交给同事的步骤说明书：任务目标、步骤要求、可用工具、依赖产出引用 |
| 前台对话 | 用户与某位同事的直接会话模式；会话按"用户 × 同事"组织，默认本人可见 |
| 被调度执行 | 编排按任务计划把步骤派发给同事执行的模式（无会话，以派发书为上下文） |
| 对话对象 | 当前会话所指向的 AI：总管（默认）或某位同事 |
| 执行窗口 | 同事完成一个步骤所使用的独立上下文（随步骤生灭） |
| 任务状态总线 | 任务的结构化状态存储（计划版本、步骤状态、产出引用），不参与对话压缩 |
| 学习记录 | 同事的程序性知识条目（经验准则），影响后续行为 |
| 工作记录 | 同事的执行历史（情景记忆），append-only |
| 临时授权 | 任务执行期间一次性 / 任务内的权限豁免，任务终态即失效 |
| 需签字 | 同事权限三级中的"人工确认"级 |

## 11. 设计来源

- **产品方向**：平台既有愿景（单对话框操作全平台、角色化、主动发现）与"AI 管家"模块（主动提醒）在此之上的任务执行延伸。
- **交互原型**：AI 同事的创建流程（基本信息 → 数据源 → 工具与动作 → 权限与审批 → 触发与频率 → 预算与配额 → 测试发布）、同事档案（职责 / 日程 / 今日做的 / 学习记录 / 绩效 / 协作对象 / 权限边界）、三级权限（自决 / 需签字 / 禁止），以及"可直接与同事对话"（同事页"点谁就和谁对话"、档案页"和某同事对话"按钮、输入框 @同事）与"对话内任务编排"均来自原型设计的直接参照。
- **代码现状**：对话运行器与工具循环、服务端程序化批准、上下文压缩、用户级记忆、企业知识库与连接器运行时，是本文档"现状约束"与"衔接设计"的事实依据。

# AI 任务编排：需求设计

> 状态：设计定稿（2026-09-28）
> 实施进展（2026-09-29）：M1 骨架已落地——数据模型、任务面契约、权限码、编排服务骨架、`create_orchestration_task` 工具与「无在职 AI 同事时编排工具不出现」的降级门控、任务接口；**M2 已落地**——子执行与窗口隔离（派发书、独立执行窗口、摘要与产出引用回流）、任务调度与断线恢复；**M3 部分落地**——交互挂起与恢复骨架、临时授权全链路（授权卡挂起、批准消费、拒绝收束、断点续跑、任务终态失效）、编排决策器抽象位（首版规则 + LLM：`orchestration_decision` 模型角色、置信度分流）、主动问人 / 裁决挂起（`ask_user` 挂起 → 答复注入断点续跑）、挂起超时策略（默认无限等待）与防滥用上限（单任务授权 / 提问次数）；**M3-F 失败阶梯已落地**——失败自动收拢与可重试分类、指数退避自动重试、超限升级用户裁决（重试 / 跳过 / 终止，选择如实落状态）；**M3-R 重编排与执行中重排已落地**——计划卡片「调整要求」生成新版本草案（`revise_orchestration_task` 工具、`revisionKey` 幂等）、失败裁决「调整计划」（任务保持挂起、对话中说明调整、新草案再次确认）、再次确认按锚点沿用已完成步骤产出（不重跑）、对话轮次自动注入"待调整任务"引导；**M4 融合与沉淀待实施**（分块见第 11 节）。

## 1. 概述

### 1.1 解决的问题

平台现有的 AI 对话链路面向"一问一答 + 工具循环"：单轮内模型建议调用若干工具，服务端程序化批准后执行，回答随流式返回。当用户请求升级为"完成一件事"（生成经营简报、批量审查合同、制作演示视频）时，现有链路在四处不足：

1. **时长**：一件事可能包含多个步骤、跨数分钟到数小时，超出单轮对话的生命周期；
2. **协作**：不同步骤需要不同职能的 AI 同事（数据收集、分析、写作、评审），单轮对话没有"分派给多人"的结构；
3. **上下文**：全部中间过程塞入单一会话窗口，会污染主线对话、推高成本、最终必然溢出；
4. **交互**：执行中需要用户参与的时刻（权限不足、信息缺失、结果裁决）没有统一的挂起与恢复结构。

本设计给出一个由服务端驱动的任务编排体系：用户发起任务，编排生成计划并调度 AI 同事逐步执行，全程状态可见、断线可恢复、需要用户参与时挂起等待，完成后产出与经验沉淀回企业。

### 1.2 与既有能力的关系（现状盘点）

| 能力 | 现状 | 本设计的动作 |
| --- | --- | --- |
| 对话与工具循环 | 已实现：轮次状态机、工具批准、流式事件、幂等与审计 | 保留为"单步执行器"；编排在其上叠加任务层 |
| 上下文压缩与用户级记忆 | 已实现：面向单会话 / 单用户 | 保留；编排新增"任务状态总线"与"执行窗口"两个空间 |
| 相关追问（推荐选项） | 服务端全链路已就绪：契约事件、生成、持久化、事件追加；桌面端尚未渲染 | 前端接入 + 抽象为统一"建议"体系（第 6.1 节） |
| 缺参追问 / 同名消歧 | 已实现：对话回合内的追问（见 [AI 助手业务写操作](assistant-business-tools.md)） | 编排步骤级的"向用户提问"在其上扩展为挂起机制（第 6.3 节） |
| 写操作确认（待确认草稿） | 已实现：写操作确认卡片、确认前无副作用 | 与"需签字"权限叠加为双层保护（第 8.4 节） |
| 任务 / 计划 / 子执行模型 | 不存在 | 新增（技术设计定义） |
| 临时授权 | 不存在 | 新增（第 6.2 节） |
| 编排决策抽象 | 不存在 | 新增"编排决策器"抽象位，首版规则 + LLM，预留 JEV 实现（第 5 节） |

### 1.3 设计原则

1. **代码驱动，模型建议**：状态机、调度、挂起/恢复、幂等、审计全部在服务端代码中；模型只产出计划草案、步骤内容与决策建议，永远不直接驱动流程。这是既有"NestJS 唯一编排中心"原则在任务层的延续。
2. **共享状态与产出，隔离执行窗口**：任务事实（计划版本、步骤状态、产出引用）与协作产物对全任务可见；每位同事的执行上下文相互隔离、随步骤生灭。
3. **读取时最新**：同事不在本地缓存企业知识、业务数据与记忆；每次执行从事实源现查现注入，"最新企业动作"由读取方式保证，而非同步机制。
4. **全程可审计**：任务、步骤、审批、授权、用户交互、产出确认均记录租户、操作者、请求、资源与元数据。
5. **可替换的决策层**：编排决策经过统一抽象位（`OrchestrationDecider`），首版以规则 + LLM 实现，后续可切换为外部决策引擎 JEV，流程代码零改动。

## 2. 对话与编排双通道

### 2.1 对话对象

对话界面只有一个，但每次会话有明确的**对话对象**：默认是总管（用户的私人代理），也可以是某位 AI 同事。入口形态（与原型一致）：

- **默认**：用户直接说事，总管处理；
- **指定**：从 AI 同事页"点谁就和谁对话"、从同事档案页点"和某位同事对话"，打开（或创建）与该同事的会话。

**会话与对话对象的关系**：一条会话固定一个对话对象（对象是会话的属性）：

| 维度 | 设计 |
| --- | --- |
| 会话粒度 | 总管会话、与某位同事的会话是各自独立的线程，各有独立的消息流与压缩摘要 |
| 历史列表 | 保留统一的历史列表（按最近活动排序），每条显示对话对象；支持按对象筛选（"只看与某位同事的"） |
| 归属 | 会话归发起用户：默认仅本人可见、企业审计可查；同事会话不例外 |
| @ 语义 | 会话内 @ 某位同事**不切换会话对象**：它是编排语义——"这件事指定由某位同事执行"（原型输入框"交给哪位 AI 同事"），结果回流当前会话；要连续多轮深聊，进入与该同事的会话 |

**为什么不支持会话内自由切换对象**：上下文、权限与压缩都是对象绑定的——总管会话含用户级记忆与私人主线；同事会话的上下文是"该同事的人格 + 学习记录 + 履历摘要"（2.2 节）。同一会话内切换对象，要么把总管的私人上下文泄漏进同事窗口（破坏隔离不变量），要么需要为每个对象维护分段消息流与分段压缩（重建复杂度成倍）。独立线程以零成本实现同样的效果，每段历史天然干净。

**为什么需要对话对象而不是多套系统**：单对话框是产品主线（用户只有一个入口、一套列表）；对话对象是会话的属性，权限过滤、历史记录、上下文组装在服务端按对象分别处理。

**两类"历史"不混淆**：与同事的对话历史属于用户会话（私人线）；同事的工作记录（她做过的事）属于企业资产，展示在其档案页。列表只是界面组织方式，记忆与记录的归属走既定模型。

### 2.2 通道 A：前台对话（与同事直接交流）

用户与同事直接对话时的上下文组装：

```
同事职能定义（工作方式、输出标准）
+ 该同事的学习记录（按相关性 + 适用范围过滤）
+ 该同事的工作记录摘要（近期做过什么）
+ 本会话的消息流（含压缩摘要）
+ 发起人自己的用户级记忆（个人偏好，如"先给结论"）
+ 工具面（权限 = 发起人权限 ∩ 同事权限上限）
+ 企业知识库检索与业务数据工具
```

要点：

- **会话归属**：会话按"用户 × 同事"组织，默认仅发起用户可见，企业审计可查；对话原文不移交企业侧。
- **权限不因"只是聊天"放宽**：对话中可用的工具与数据范围同样受"发起人 ∩ 同事上限"约束；触达"禁止"级边界时，同事说明边界并给出替代方案。
- **"需签字"级动作**：用户正处对话中，直接以确认卡片征求同意（复用写操作确认模式），不涉及"任务期临时授权"。
- **对话可以升级为任务**：见 2.4。

### 2.3 通道 B：编排执行（任务模式）

用户在任意对话中提出复杂请求时，系统判断"是否需要多步骤编排"（原型 `isOrchestrationWorthy` 的职责在服务端承担）：

- **不需要**：走现有单轮对话链路（回答 + 工具调用）；
- **需要**：进入任务编排（第 3 节）——总管生成计划、服务端派发、同事逐步执行、结果汇总回对话流。

**为什么复杂请求要有独立的执行轨道**：任务的生命周期长于一轮对话（可能跨小时、跨终端、断线续做），且执行过程不应占用主会话上下文。任务以"结构化状态"存在于数据库中，对话只是它的展示与控制面。

### 2.4 会话到任务的转化

两条通道不是互斥的，而是同一条流水线的两个入口：

| 起点 | 过程 | 结果 |
| --- | --- | --- |
| 用户向总管提出复杂请求 | 总管识别 → 生成计划 → 派发执行 | 任务 + 会话中的执行时间线 |
| 用户在同事对话中提出超出单步能力的请求 | 同事识别 → 转交编排（用户确认） | 任务（该同事通常为执行者之一） |
| 任务完成后用户追问（在任何相关会话内） | 注入任务产出引用回答 | 一般对话；若触发修改/新步骤则生成新计划版本 |

任务的产出对相关同事的前台对话可见（作为产出引用注入），保证"她记得自己做过什么"。

## 3. 任务全流程

### 3.1 流程总览

```
用户发起（对话/同事会话/自动触发）
   │
   ▼
① 意图理解与复杂度判断 ── 简单 → 单轮对话链路（不建任务）
   │ 复杂
   ▼
② 计划生成（总管：目标、步骤序列、执行同事、数据来源、产出物）
   │
   ▼
③ 派发前确认（展示完整计划步骤清单 + 关键待定项顺带澄清（如产出格式）；用户确认后才开始执行）
   │
   ▼
④ 逐步执行循环（每步：派发 → 同事在独立窗口执行 → 结果写回状态总线 → 决策点检查）
   │   ├─ 需用户参与 → 挂起（授权 / 提问 / 裁决），恢复后继续
   │   ├─ 步骤失败 → 自动退避重试 / 升级用户裁决（重试 / 跳过 / 终止 / 调整计划）
   │   │                └─ 调整计划 → 对话说明调整 → 新版本草案回到 ③ 再次确认（已完成步骤沿用产出）
   │   └─ 产出草稿 → 用户预览、修改、确认
   │
   ▼
⑤ 完成汇总（总管汇报：做了什么、产出在哪、需要关注什么）
   │
   ▼
⑥ 沉淀（产出入企业资产；工作记录写入；学习记录候选提取）
```

### 3.2 示例走查：生成经营简报

以"生成本周经营简报"为例走完一遍流程（对照原型对话内编排的展示形态）：

1. **发起**：用户在总管对话中说"生成本周经营简报"；
2. **复杂度判断**：识别为多步骤任务（数据收集 → 分析 → 撰写 → 生成交付稿）；
3. **计划生成**：总管产出计划草案——完整步骤清单对用户可见（如：① 收集销售数据（数据同事）② 分析经营趋势（分析同事）③ 撰写简报（文档同事）④ 生成交付稿（文档同事）），涉及 3 位同事、数据来源（CRM、财务系统、上周简报）；生成中发现"简报格式（PPT / Word）"未指定——它直接决定写作结构与生成链路，属于关键待定项，顺带在计划卡片中以选项形式问用户；
4. **派发前确认**：对话内展示"开始前确认一下"卡片：完整步骤清单（每步做什么、谁来做）+ 5 步 · 约 12 分钟 · 3 位同事 · 会读取这些数据 · 产出这些文件 · 只读取你权限范围内的数据；用户选定格式并点"开始"后**才开始执行**（未确认不派发）；也可点"调整要求"（回到输入框补充约束，计划随之更新）；
5. **逐步执行**：对话流与侧栏工作区同步展示每一步——哪一位同事、做什么、读了什么数据、结果摘要；无依赖的步骤可并行；
6. **决策点**：某步需要用户裁决（如"简报是否包含华东区专项分析"）→ 挂起为待裁决卡片，其余步骤继续；
7. **完成汇总**：产出以草稿出现（可预览、编辑、让 AI 改、版本留痕），确认后归档入知识库（默认建议部门库、可改；规则与可见范围提示见 3.5 节）；有对外发送类动作则走"需签字"确认；
8. **沉淀**：任务摘要写入相关同事的工作记录；从用户反馈（如"简报 3 忧太多"）提取学习记录候选。

### 3.3 计划生成与派发前确认

**计划内容**：目标描述、步骤序列（每步：职责、执行同事、输入引用、预期产出）、使用的数据来源、产出物清单、预估。

**计划对用户可见**：计划草案生成后，对话内展示**完整的步骤清单**（逐步列出"做什么、谁来做"），而不是只给"5 步 · 12 分钟"的汇总数字——用户要确认的是"怎么干"，必须看得到每一步；该清单在执行阶段自然转为任务时间线（步骤视图）。

**关键待定项顺带澄清**：计划生成时若存在"影响后续所有步骤、且无法安全默认"的关键缺口（典型：产出格式——经营简报是 PPT 还是 Word，直接决定写作结构与生成链路），在计划卡片中以选项形式顺带问用户，答复随确认一并提交、计划随之落定；能稳妥默认的参数（时长预估、读取范围）不单独发问，在卡片上标注默认值即可改。判断标准是"问一次能否省掉返工"——在计划阶段问格式，省掉的是"写完才发现格式不对"的整链返工；执行到生成步骤才问，前序步骤全部白跑。

**派发前确认**（原型的"开始前确认一下"）是编排的默认交互，也是执行的闸门：**计划未经用户确认不派发**（任务类型配置了自动采纳的除外）。卡片内容：完整步骤清单 + 关键待定项澄清 + 数据来源与权限范围（"只读取你权限范围内的数据"）+ 产出物 + 预估。目的有三个：让用户确认"怎么干、要读哪些数据、产什么、大概多久"；给用户"调整要求"的入口（避免跑完才发现理解偏差）；把权限范围显性化。**"调整要求"与执行中失败后的"调整计划"走同一条重编排链路**：对话中说明调整内容 → 总管生成新版本草案 → 卡片再次确认后才物化执行（已完成的步骤按锚点沿用产出、不重跑）。

**为什么由模型生成计划、由代码承载计划**：计划是"草案"，必须经用户确认（派发前确认）或直接采纳后才生效；生效后的计划存入任务状态（可版本化），后续调度以状态中的计划为准——模型的生成物一旦落库，就成为代码的事实源。

### 3.4 逐步执行与过程展示

每一步的执行遵循同一模式（技术上复用现有单步执行器）：

1. 服务端组装**派发书**（任务目标、本步要求、可用工具、依赖产出的引用、相关记忆）；
2. 派发后，同事在**独立执行窗口**内完成本步（可多轮工具调用）；
3. 结果（摘要 + 产出引用）写回任务状态；
4. 决策点检查（是否需要用户参与、是否继续下一步、是否需要重编排）——重编排的两种入口：用户主动（计划卡片「调整要求」或对话中直接提出调整）与失败升级（裁决选择「调整计划」，任务保持挂起等待用户在对话中说明调整内容）。

**过程展示**（原型形态）：对话流内以"工具调用"样式逐步展示步骤执行（哪位同事、做什么、数据源、结果）；侧栏工作区提供"步骤 / 产出 / 依据 / 拍板"视图——依据页回答"这个结论读了哪些数据"，拍板页集中处理待裁决事项。

**为什么展示要"步骤级"而非"消息级"**：用户要的是"这件事办到哪了、每一分结论的依据是什么"，结构化步骤视图天然满足；同时它也是断线恢复的界面载体（回来接着做）。

### 3.5 完成、汇总与产出验收

- **汇总**：任务完成后由总管在对话流中汇报：完成了什么、产出清单、执行中的关键依据、需要关注的事项；
- **产出草稿制**：产出不以"最终版"直接入库，而是先以草稿呈现——用户可预览、直接编辑（记版本）、让 AI 修改；确认后归档入知识库（原型中该资料体系的入口名为"空间"，即既有知识库体系，不引入新的存储概念）；
- **归档随验收一并确认**：确认卡同时承载"内容确认"与"归位确认"；
- **对外动作**：发送、发布等动作按权限三级处理（"需签字"挂起确认、"禁止"拒绝）。

**为什么产出要"草稿 + 确认"**：AI 产出具有不确定性，企业数据要有明确的责任人（确认人）；草稿机制让"AI 干活、人负责"落在流程上，而不是靠事后追认。

**归档规则（入哪一级知识库）**：企业资料按四级知识库组织——个人库、部门库、项目库、公司库（归属级别为知识库既有模型）。归档目标按下述规则产生：

| 发起情形 | 归档目标 |
| --- | --- |
| 有明确部门归属（员工 / 部门负责人发起） | 默认其所属部门的知识库；部门尚无库时提示创建或另行选择 |
| 属于项目上下文的任务 | 建议项目知识库（用户可改） |
| 无部门归属或产出与部门无明确关联（如老板 / CEO / 跨部门角色） | 不猜测：AI 基于产出主题从"用户可归档的库"（权限过滤后）给出候选，请用户选择 |

**归档必经用户确认**：任何情形都"先建议或先回答、再确认、后落库"——有默认建议时，卡片显示"将存入：销售部知识库（可修改）"；无明确归属时，卡片先请用户选择存储位置（AI 提问 → 用户回答），随后卡片更新为"将存入：XX（确认后归档）"，用户确认才实际转存。归档人须对目标库具备编辑 / 管理权限（沿用知识库现有权限模型），候选中绝不出现其无权限的库。

**确认卡显性提示可见范围**：存入哪一级库决定谁可以检索到它——公司库全员、部门库本部门、项目库项目成员、个人库仅本人；提示直接展示，避免"内部资料误放公司库"。

**为什么归档要分级别 + 确认**：产出一旦入库就成为可检索资产（后续同事干活、对话检索会按权限读到它），归档错了只有两种后果——"内部资料外扩"或"该共享的没共享"；所以默认给组织血缘推断（部门的人归部门），无血缘不猜（问用户），落库前最后一次确认把误放风险压到零。

### 3.6 沉淀（详见第 7 节）

任务终态后：产出归档入知识库（规则见 3.5 节）；相关同事写入工作记录（摘要级）；满足条件的经验提取为学习记录候选；任务执行的组织暴露"同一属性的活重复发起"时可提示复用近期产出（效率优化，非一致性要求）。

## 4. 上下文与工作记忆

### 4.1 三个空间

| 空间 | 内容 | 生命周期 | 压缩策略 |
| --- | --- | --- | --- |
| 主会话流 | 用户与总管（或同事）的对话消息 | 会话级 | 沿用现有压缩：超阈值后 LLM 摘要 + 保留近期消息 |
| 任务状态总线 | 任务、计划版本、步骤状态、产出引用、挂起事项 | 任务级（持久化） | **不做 LLM 压缩**；结构化存储，每次调度现读 |
| 执行窗口 | 单步执行的上下文（派发书 + 依赖产出 + 相关记忆 + 本步工具循环） | 步骤级（随步骤生灭） | 天然短：不携带历史对话，不需要压缩 |

### 4.2 共享与隔离的分界线

```
                共享（白板）                 |        隔离（大脑）
  ─────────────────────────────────────────┼──────────────────────────
   任务状态（计划、步骤、进度）              |
   产出物（草稿与确认版，按权限可见）         |   各同事的执行窗口
   同事资产（职能、学习记录、工作记录）只读    |   各用户的主会话流
   挂起事项（授权、提问、裁决）              |
```

- **共享**：任务相关主体（发起人、参与同事、被分享者）通过任务状态与产出协作；同事之间以"读取状态 + 产出引用"的方式接力，不存在同事间的消息传递。
- **隔离**：执行窗口与主会话流互不注入对方原始消息；跨空间的信息搬运只允许"摘要 + 引用"两种形态。

### 4.3 三个不变量

1. **任务进度只以任务状态为准**：任何"刚才做到哪了"的答案都来自状态总线，不依赖任何模型记忆或对话历史；
2. **执行窗口靠隔离保证纯净**：子步骤不共享总管窗口，也不共享其他步骤的窗口；需要的上下文以派发书显式传入；
3. **回流永远是摘要 + 引用**：步骤结果回写状态时只存"摘要 + 产出/依据引用"，原始长文本留在产出资产中，供需要时按引用读取。

**为什么是这三条**：它们分别对治多 Agent 系统的三个常见失控——进度失忆（重启后不知道干到哪）、上下文互相污染（B 步骤被 A 步骤的过程带偏）、上下文膨胀（全量结果层层累加）。

### 4.4 为什么不让子步骤共用总管窗口

- **污染总管决策**：总管要基于任务全局做"下一步 / 要不要问人 / 完成没有"的判断，若窗口里混入各步的原始过程，关键事实会被噪声稀释；
- **消息结构无法安全重建**：工具调用消息与工具结果必须成对出现，从别处搬运原始消息重建上下文极易产生结构不完整（被服务商拒绝或行为异常）；
- **安全面扩大**：不同步骤的原始过程可能包含不同权限级别的数据（如薪酬明细），共享窗口会让低权限步骤"顺带看到"高权限数据。

## 5. 编排决策（JEV 的角色）

### 5.1 先纠正三个常见误解

1. **不是"LLM 把信息交给 JEV，JEV 返回调度计划"**：JEV 不生成计划、不返回计划。计划由 LLM 生成（经用户确认后落库）；JEV（或首版的规则 + LLM 实现）只在流程的关键节点回答原子问题。
2. **不是"LLM 去调度"**：调度（派发、循环、挂起、恢复、重试、超时）全部是代码行为；LLM 的产物只有"计划草案、步骤内容、面向用户的话术"。
3. **不是"JEV 全知全能"**：JEV 是决策引擎（以 Choice / Score / Noul 等原子决策原语为接口、返回带置信度的选项），它的职责仅限于"原子判断"；中文内容生成、长文写作弱于 LLM，因此两方按"判断归 JEV、生成归 LLM"分工。

### 5.2 三方职责

| 角色 | 类比 | 职责 |
| --- | --- | --- |
| 服务端代码 | 司机 | 状态机、派发、挂起/恢复、幂等、重试、超时、审计、事件推送；调用决策器拿建议并执行 |
| LLM | 规划师 + 工人 | 生成计划草案、生成步骤内容与产出、理解自然语言、生成对用户的话术（问什么、建议什么） |
| 决策器（JEV 或规则 + LLM） | 红绿灯 | 在关键节点给出原子判断与置信度：完成判断、路由（下一步/问人/重排）、质量风险评分、重编排触发 |

### 5.3 决策类型与置信度分流

编排中需要"判断"的原子问题（首版由规则 + LLM 实现，可替换为 JEV）：

| 决策点 | 问题 | 示例 |
| --- | --- | --- |
| 完成判断 | 该步骤的产出是否达标？任务目标是否达成？ | 简报数据齐全、格式合规 → 完成 |
| 路由 | 下一步做什么？ | 继续下一步 / 需要重排 / 需要问人 / 直接完成 |
| 信息充分性 | 是否缺少关键信息或存在歧义，必须问用户？ | "华东区"指哪个组织维度 |
| 质量与风险评分 | 产出质量分、风险等级 | 对外文本的合规风险评分 |
| 重编排触发 | 是否需要修改计划（增删步骤、换执行顺序）？ | 数据源不可用 → 插入"更换数据源"步骤 |

**置信度分流**（沿用 JEV 的思路，首版同样适用）：

- 高置信（如 > 0.9）：按建议自动执行，记入审计；
- 中置信：走保守分支（继续但标记需复核，或向用户发起轻量确认）；
- 低置信：升级为用户裁决（挂起提问），不自行冒险。

阈值可配置（按租户 / 任务类型）。

### 5.4 抽象位与演进

编排代码只依赖统一的**编排决策器**接口（输入：任务状态快照 + 决策类型；输出：选项 + 置信度 + 理由）。演进路径：

- **v1（首版，已落地）**：规则 + LLM 实现——确定性场景用规则、模糊场景用 LLM（带结构化输出约束）；首版规则路径先覆盖信息充分性判定（防滥用超限 / 同类去重）与失败阶梯判定（可重试分类 + 尝试余量：可重试未超限 → 自动重试，否则 → 升级用户），完成判断、重编排触发等场景随重编排实施接入；
- **v2**：接入 JEV 实现同一接口，按置信度分流直接替换，流程代码零改动。

**为什么要先抽象再实现**：决策质量是长期演进的变量（规则 → LLM → 专用决策引擎），而流程骨架是稳定资产；两者解耦后，决策层可以独立升级与回退。

## 6. 用户交互

编排中的三类用户交互共享同一套"挂起 / 恢复"骨架，区别只在于触发原因与卡片形态。

### 6.1 建议（追问与开场建议）

**形态**：AI 给出可点击的选项（点一下即发送，替代用户打字）；两个场景共用一套抽象：

| 场景 | 时机 | 内容来源 |
| --- | --- | --- |
| 轮后建议（follow-up） | 一次答复完成后 | 随本次回答顺带生成（现有 ai-service 能力），如"要我把这份简报转成 PPT 吗" |
| 开场建议（starter） | 尚未开始对话时 | 按用户权限筛选可用场景 × 企业动作摘要（近期动态、进行中任务）生成，如"你关注的星海制造有新动态" |

**统一抽象**（不耦合于任一场景）：建议 = {场景, 文本, 排序, 来源, 状态, 过期时间}，由可插拔的 Provider 生成；权限硬过滤——**绝不出现用户无权执行的建议**。

**与现状的衔接**：轮后建议的服务端链路已就绪（契约事件 `related_questions` 在答复完成后异步到达、持久化；参见 [公开 AI 对话链路与 Token 计量](../architecture/public-chat-api-and-token-metering.md)）；本次改造包括：桌面端渲染接入、任务场景扩展（任务完成后给出建议）、开场建议落地（权限筛选 + 企业动作摘要 + 短 TTL 缓存）。

### 6.2 临时授权申请

**触发**：同事执行到"需签字"级动作（或权限不足的步骤）时。典型场景：任务最后一步需要对外发送；员工临时需要一项超出同事职能上限但自己有权做的操作；连接器未完成授权。

**流程**：

1. 该步骤挂起（**不阻塞无依赖的其他步骤**）；对话流 / 收件箱推送授权卡片：谁、要什么、为什么、影响范围；
2. 用户选择"仅本次 / 本任务内允许"或拒绝；
3. 批准后临时生效，恢复该步骤；
4. 申请、决定、使用三段全量记录并进入审计。

**两条硬约束**（安全需求）：

- **仅任务期生效**：临时授权绑定任务，任务到达终态（完成 / 失败 / 取消）即失效；下一次同类任务需重新申请；
- **全量记录**：申请者、审批者、时间、被批准的权限、被用在哪个步骤，全部可审计回溯。

**边界**：临时授权不能突破同事的"禁止"级边界（治理红线不可由单次审批豁免）；粒度只有"仅本次"与"本任务内"两种，不提供"长期授权"（长期需求走角色 / 成员权限的正规变更流程）。

**防滥用**：同一任务内同类申请合并为一次；单任务申请次数有上限（超限升级人工）；用户拒绝后同任务内不自动重试（除非用户主动重新发起）。

### 6.3 AI 主动问人（信息缺失与歧义）

**触发**：三类时点——（1）**计划阶段的关键缺口**：如产出格式等"影响后续所有步骤且无法安全默认"的待定项，顺带在计划确认卡片中问，答复随确认提交（见 3.3 节，不进入步骤级挂起）；（2）**执行中的缺信息与歧义**：缺关键信息、存在歧义、或出现必须由用户拍板的分岔（两类方案都可行且代价接近）；（3）**失败处置升级**：步骤自动重试超限或遇到不可自动重试的失败时，把"重试 / 跳过 / 终止 / 调整计划"交给用户拍板（见 8.1 节）；选择「调整计划」后任务保持挂起，用户在对话中说明如何调整，据此生成新版本草案、再次确认后继续。

**三段分工**（与第 5 节职责表一致）：

| 环节 | 负责方 | 说明 |
| --- | --- | --- |
| 判断"要不要问" | 决策器（信息充分性 / 路由判断） | 缺信息、歧义、分岔、低置信度时建议挂起 |
| 生成"问什么" | LLM | 问题、说明、候选人选项（如"华东区：按大区组织 / 按门店归属"） |
| 挂起 / 恢复 / 超时 | 代码 | 步骤转 WAITING_USER、推送事件、等待答复、超时策略 |

**恢复语义**：用户答复作为"步骤输入"注入执行窗口，从中断点继续（而非重头执行）。**超时策略**：默认无限等待（重要任务不丢），可配置为"超时后按默认值继续 / 跳过该步骤 / 终止任务"。

**防滥用与克制**：同一问题只问一次，同类未决问题不重复发问；能从上下文推断或有安全默认值的自行处理，不打扰用户；单任务提问 / 裁决次数有上限（默认 10，超限转为按现有信息继续并记录），与授权申请同一护栏体系。

**与"缺参追问"的关系**：现有对话链路的缺参追问发生在单轮对话内（模型直接问、用户直接答）；编排中有两个时点——计划阶段的缺口在确认卡片中顺带澄清（随确认提交、不挂起），执行中的缺口升级为步骤级挂起——跨轮次、跨终端可达（用户在手机上也能答复），且不阻塞任务其他部分。

### 6.4 统一模式：挂起与恢复

三类交互（建议除外）本质都是**任务级挂起**：任务进入"等待用户"的心智状态（具体挂起点精确到步骤或决策），推送卡片 → 用户操作 → 事件恢复 → 状态机继续。设计要点：

- **挂起不冻结全任务**：只挂起相关步骤，无依赖步骤继续；
- **挂起可多开**：多个步骤可分别等待不同用户输入；
- **恢复幂等**：同一答复的事件重复投递不产生二次执行；
- **调整计划让行**：失败裁决选择「调整计划」后任务保持"等待用户"（不自动恢复执行），直到新版本草案生成并再次确认——避免在用户说明调整内容前被调度续跑；
- **终态清理**：任务取消 / 完成时，未处理的挂起事项自动关闭并通知。

## 7. 同事知识与记忆同步

### 7.1 数据来源模型

同事工作时（两种模式）的数据来源统一为五类，与"不复制文档知识"的定位一致：

| 来源 | 内容 | 获取方式 |
| --- | --- | --- |
| 企业知识库 | 文档、制度、决策历史 | 检索工具（RAG），权限过滤 |
| 业务数据 | CRM / 财务 / 项目 / 会议等 | 工具实时查询（不灌入上下文、不落库） |
| 同事经验 | 学习记录 | 按相关性 + 适用范围过滤后注入 |
| 同事履历 | 工作记录 | 近期摘要注入；完整历史按需查询 |
| 任务与用户上下文 | 任务状态 / 用户偏好 | 编排注入（派发书）；前台对话注入发起人自己的用户记忆 |

### 7.2 任务完成后的沉淀

任务终态后按"归谁所有"三类处理：

1. **产出资产**：用户确认后的版本归档入知识库的既定级别（个人 / 部门 / 项目 / 公司，规则与确认流程见 3.5 节）；产出文件本体留在资源体系（预览 / 下载入口不变），知识库侧生成可检索条目；
2. **工作记录**：参与同事各写入一条摘要（任务、发起人引用、时间、涉及步骤、产出引用、结果）；
3. **学习记录候选**：显性反馈（用户明确纠正 / 表扬）与隐性信号（重复修改同一类问题、错误纠正）提取为候选；按适用范围规则生效（对该用户 / 全局 / 特定场景），高影响变更需职能负责人确认。

**所有对人的引用使用成员实体 ID，不存姓名字符串**：成员离职、换岗、改名后，历史记录仍指向同一实体，展示层实时解析；审计场景由事件快照还原历史时刻。

### 7.3 多人并发与一致性

- **同一同事被多人同时调用**：每次调用是独立实例（执行窗口 / 会话各有归属），资产只读共享；无需锁；
- **同一属性的活被并发执行**：并行产出合法；编排可检测"近期相关产出"提示复用（效率优化）；
- **完成先后顺序**：不需要协调——同事不缓存知识，后启动的执行读到的事实天然包含先完成者的结果（读取时最新）；
- **写入冲突**：工作记录、学习记录、产出均 append-only，没有原地覆盖的冲突点。

## 8. 失败、恢复与安全

### 8.1 失败处理

步骤失败的处置阶梯（决策器给建议、代码执行）：自动重试（有限次，指数退避）→ 更换数据源 / 参数重排 → 标记跳过（产出缺失说明）→ 升级用户裁决。跳过与重排都记录在任务状态中，汇总时如实呈现。

已落地形态（M3-F）：所有失败入口（执行异常、执行失联、超时收束）先统一记为"步骤失败"，再按错误性质集中处置——可重试类错误自动退避重试（上限默认 3 次含首次；退避 30 秒起步、逐次翻倍），到达上限或不可重试类升级为用户裁决：给出"重试 / 跳过 / 终止"三个选项，选择如实落到任务状态（"跳过"标注产出缺失、"终止"记为失败并注明用户终止、不再自动处置）；退避等待期间任务让出执行资源，到点自动续跑。**「调整计划」（M3-R 已落地）**：裁决提供第四选项「调整计划」——选择后任务保持挂起让行，用户在对话中说明调整要求，总管经 `revise_orchestration_task` 生成新版本草案（幂等），任务回到"待确认"，确认后物化新版本继续执行；已完成的步骤按沿用锚点复用产出、不重跑。系统自行决定改计划的自动重排不在当前范围——重排由用户驱动。

### 8.2 中断恢复

任务状态持久化在数据库，与任何客户端连接解耦：

- 用户关闭客户端后任务继续执行（服务端驱动）；
- 用户回来时从任务列表 / 对话时间线恢复视图（原型状态：进行中 / 等你拍板 / 已完成 / 未完成）；"未完成"的任务可从离开时的步骤继续；
- 服务重启后，未完成任务按状态机继续（已完成的步骤不重复执行）。

### 8.3 幂等与审计

- 步骤执行与工具调用沿用既有幂等键机制，重复事件不产生二次副作用；
- 全链路审计：任务创建、计划确认、每次派发、工具调用、挂起与恢复、授权申请 / 决定 / 使用、失败处置判定、产出确认；记录租户、操作者、请求、资源与元数据。

### 8.4 权限与额度

- 权限：执行与对话统一使用"发起人权限 ∩ 同事权限上限"（三级：自决 / 需签字 / 禁止）；数据范围不绕过既有数据范围解析；权限码按功能新增（编排查看、任务管理、授权审批等）；
- 额度：沿用现有额度体系（企业共享池，会话 / 轮次 / 成员计量），任务执行按现有口径记录用量，不引入新的计费维度。

## 9. 与既有系统的关系

| 既有系统 | 关系 |
| --- | --- |
| AI 管家（主动提醒） | 职责互补：管家负责"发现与提醒"（规则驱动的事找人）；编排负责"执行"（任务落地）。衔接点：提醒卡片可一键转为任务（后续扩展） |
| 通知中心 | 挂起事项（授权 / 提问 / 裁决）通过通知与收件箱触达用户；通知只是触达渠道，事实仍在任务状态中 |
| 用户级记忆 | 前台对话注入发起人自己的记忆；任务执行不注入（执行遵循职能准则） |
| 连接器运行时 | 任务步骤中的连接器工具调用沿用既有发现与执行链路（含按用户维度的授权） |
| 角色化首页 / 工作台 | 任务时间线可汇入工作台的"进行中事项"视图 |

（明确的非目标：本文档不改变 AI 管家、通知中心、连接器的既有职责与实现。）

## 10. 验收口径

1. **双通道**：用户可与任一有权限的同事直接对话；对话中可升级为任务；任务产出可在相关对话中回溯引用。
2. **计划与确认**：复杂请求生成计划草案，用户可看到完整步骤清单；关键待定项（如产出格式）在确认阶段顺带澄清；**未经确认不执行**；确认前的任何展示不产生副作用；计划调整（主动「调整要求」或失败后「调整计划」）生成新版本草案并再次确认，已完成的步骤沿用产出、不重跑。
3. **过程可见**：执行中可看到"哪位同事、哪一步、读了什么数据、结果如何"；产出以草稿制验收，归档位置与可见范围经用户确认后入知识库。
4. **挂起恢复**：权限不足 / 信息缺失 / 需裁决时挂起对应步骤，推送卡片；答复后从断点继续；不阻塞其他步骤。
5. **临时授权约束**：仅任务期生效、任务终态失效、全量审计；不可突破禁止级。
6. **断线续做**：关闭客户端不影响执行；返回后可查看进度并继续未完成任务。
7. **沉淀正确**：任务完成后工作记录写入、学习记录候选提取；对人的引用为成员实体 ID。
8. **安全底线**：全程"发起人 ∩ 上限"；幂等防重；审计可回溯每次操作与授权。
9. **决策可替换**：编排决策经过抽象接口，行为可通过替换实现（规则 + LLM → JEV）演进。

## 11. 实施分块建议

功能全景以本文档为准；实施按以下分块推进，每块独立可验证：

| 分块 | 内容 | 验证 |
| --- | --- | --- |
| M1 | 任务 / 计划 / 步骤模型与计划生成：意图识别、计划草案、派发前确认、任务状态机与服务端驱动 | 服务端测试 + 对话内最小闭环 |
| M2 | 子执行与窗口隔离：派发书组装、执行窗口、逐步执行、摘要回流、产出草稿制 | 多步任务闭环 + 断线恢复 |
| M3 | 重编排与交互：编排决策器抽象位、步骤级挂起（临时授权 / 主动问人 / 裁决）、失败阶梯、计划重编排（调整要求 / 执行中重排与沿用产出） | 挂起恢复场景全量 |
| M4 | 融合与沉淀：建议系统（前端渲染 + 任务建议 + 开场建议）、过程展示完善（依据 / 拍板视图）、工作记录与学习记录写回、复盘 | 端到端验收 + 建议权限过滤 |

## 12. 设计来源

- **讨论定案**：主管-工人架构、三层上下文与三不变量、JEV 三方职责与置信度分流、建议系统抽象、临时授权硬约束、学习记录实体引用等均来自本设计周期的结论。
- **交互原型**：对话内任务编排（步骤展示、开始前确认、产出草稿、决策卡）、AI 同事页与档案页的对话入口、输入框 @同事、权限拒绝与"发起授权申请"、任务中断续做的状态标注。
- **代码现状**：对话轮次状态机与工具循环、程序化批准、上下文压缩、用户级记忆、`related_questions` 追问链路、写操作确认、审计与幂等机制（详见第 1.2 节盘点）。

## 1. 需求出发点：为什么做这个模块

### 1.1 一句话讲清楚

**把平台从"你问它答的工具"变成"有个管家一直替你盯着事"。**

现在用户跟 AI 的关系是：用户不开口，AI 永远沉默。目标形态是：AI 自己发现"这里有事要管"→ 主动找上对的人说清楚（为什么找、依据是什么、建议怎么办）→ 用户一句话回应（或者授权 AI 去办）→ AI 把事情跟到闭环。

目标形态速写（用于理解需求出发点）：

- 财务负责人早上打开客户端，看到助手夜里帮他理好的两件事：一笔付款卡了 5 天、一份合同还剩 7 天到期——每件都附"为什么提醒你"；
- 他点开其中一件，助手在对话里接着说："要不要我起草一份催办？"他回一句"好"，确认后助手去办，办完给回执；
- 几天后另一件事自行解决了，管家把它悄悄关掉，不再提起；
- 他嫌某类提醒吵，说一句"报销的事以后别提醒我"，这句话被写进提醒设置，从此真正安静下来。

这是一个**产品形态的转变**：平台从"人主动来操作的系统"变成"系统主动来找人"。

### 1.2 核心命题：事找人，不是人找事

这个命题决定了本模块的一切设计，写在最前面。

**平台已经不缺"看板"了。** 工作台（`/dashboard/home`、`/dashboard/todos`）、角色化首页、各类统计页都已存在。这些页面的共同模式是**人找事**：用户主动打开页面、主动巡查、主动判断"我该干什么"。但现实中：

- 人不会天天去巡查，事情不会因为有看板就自动推进；
- 看得见的所有事里，哪件急、哪件有坑、哪件其实有人正在处理——用户自己判断的成本很高；
- 出了问题，往往已经是几天后（"合同怎么还没推进？"），而不是苗头阶段。

**真正的缺口是"事找人"**：由系统承担"盯"的责任，把注意力变成系统主动送达的东西。人的注意力是最稀缺的资源——系统必须省着用它、主动供给它。

因此本模块的形态不是"又一个页面"，而是：**AI 主动开口 + 用户一句话回应 + AI 跟进到闭环**。用户感知到的应该是"有个助理在帮我盯着"，而不是"我又要维护一个清单"。

### 1.3 定位与边界

本模块的定位边界如下，后续设计不得越界。

**本模块要做的：**

| 要做的 | 说明 |
| --- | --- |
| 主动发现 | 系统持续盯着平台里"该管的事"，不依赖用户开口 |
| 主动送达 | AI 带着"为什么"找上该管的人 |
| 推动闭环 | 事情没被处理就持续跟进，处理完有结果记录 |
| 一句话处理 | 用户回一句话（看详情、去处理、不用管、让 AI 去办），不用进任何"操作台" |

**明确不做的（含原因）：**

| 不做 | 原因 |
| --- | --- |
| 独立的大型看板页面 | 平台已有工作台和角色化首页，再加页面只是让用户多一个要"逛"的地方，没有解决"人不会去看"的根本问题 |
| 统计报表、数据导出 | 报表回答"已知问题"（这个月花了多少）；管家回答"未知问题"（有笔付款卡了 5 天）。两者是不同的东西，报表演进路线见[工作台与数据看板](dashboard-workbench.md) |
| 面向终端客户的"规则编辑器" | 那是做规则引擎 SaaS 的思路。规则是产品能力（由产品/运营维护），不是让每个客户自己 DIY 的配置项；租户级阈值调整作为未来扩展点保留 |
| 每日简报式的"内容策展" | 那是消费级玩法（见附录 A 的 Pulse）。本模块面对的是企业事务，纪律是"少而准"，不是"每天投喂一堆内容" |

**一个 AI 原则：** 平台对用户始终只呈现一个 AI 助手——对话是用户与它交互的地方，管家是它的主动能力。两者是同一个身份、同一套长期记忆、同一套工具与权限，不存在"管家 AI"和"对话 AI"两个大脑、两个入口。管家不新建独立客户端、独立页面或独立会话；提醒以轻量方式送达（见 2.3、2.4、5.5），处理动作始终回到对话完成。

**术语约定**（本文档全文遵守，未来产品文案也应遵守）：

| 术语 | 含义 | 不用的说法 |
| --- | --- | --- |
| 管家 | 本模块的产品名，AI 在这件事里的角色 | — |
| 跟进事项（follow-up） | 管家正在替某人盯着的一件具体的事 | "待办/代办"（带静态清单联想，弃用） |
| 提醒 | 一次动作：AI 第一次找上用户并说明某事 | — |
| 推动 | 持续动作：事情未处理，AI 按策略再次找人 | "升级找人"（长期无人处理时找其上级）属跨人协作方向，本期不做，见 2.9 |
| 回执 | 闭环动作：事情办完了，把结果告知发起/相关的人 | — |

### 1.4 现状盘点：为什么"上下文和记忆不是瓶颈，主动链路才是"

这条结论来自对现有代码的完整盘点，是立项的直接依据：

| 主动链路需要的段 | 现状 | 说明 |
| --- | --- | --- |
| ① 发现（定时/事件触发，找到该管的事） | **有一半** | 后台任务框架（60 秒轮询 + Redis 分布式锁）、日/月指标快照、8 条首页异常规则都已存在；但任务内容是写死的（日报提醒、合同到期），且没有"发现问题单" |
| ② 判断（要不要提醒、提醒谁、怎么说） | **没有** | 后台任务里没有任何 LLM 调用通路；AI 只活在"用户发起的对话轮次"里 |
| ③ 送达（把话送到人面前） | **有一半** | 通知中心能送（站内、dedupKey 幂等、多接收人），但它只能送"死文案"，且语义是"通知"不是"跟进" |
| ④ 记录（关联上下文与记忆） | **有基础** | 会话存储、用户记忆注入方法、审计体系都是现成的复用件 |

**结论：** 上下文压缩、用户级记忆、知识库都已经能支撑"AI 懂用户、懂公司"，不需要为主动能力做架构改造。真正要从零补的，是"触发 → 判断 → 送达 → 闭环"这条主动链路。本模块不重做记忆和压缩，只做这条链路——这是本设计范围控制的第一原则。

另外一个与记忆有关的结论：**AI 的行为史靠"查"不靠"记"**——工具调用、已执行动作、跟进记录本身就是结构化数据，需要时用查询回答，不写进 30 条个人记忆（详见 2.6）。

### 1.5 与现有"工作台待办"的关系

现有 `/dashboard/todos` 是"人找事"的被动聚合（把任务/报告/会议的列表拼在一起等人来看），本模块是"事找人"的主动机制。两者并存、各司其职：

- 工作台待办：用户主动打开工作台时看到的数据视图，**本期不改造**；
- AI 管家：由系统主动发现、判断、送达、跟进，**本模块的主体**。

未来如果管家足够可靠，工作台待办可以考虑逐步收敛为"管家视图"的一种呈现，但那不是本期的事，且不得反过来让管家退化成一个新列表页。

### 1.6 市面参考（详情见附录 A）

主流产品已在做的事情：ChatGPT Pulse（每晚异步研究 → 晨间卡片 → 点赞/点踩塑造内容）、Microsoft Copilot（提醒 + 数量上限）、飞书 aily（逾期任务定向提醒、每日工作总结主动送达）、钉钉（审批 AI 风险提示）、企业微信 AI 盘客（每日清晨推送重点跟进名单）、豆包工作 × 飞书团队 Agent（"到期提醒负责人、没人响应时主动推动"）。

五条共性结论（直接约束本设计）：

1. **发现用规则/信号，AI 只做表达**——连安全运营、销售风控这些最硬核的领域都是这个架构；
2. **可扫读的"一览"是主流呈现形式**（卡片式、可展开、可追问），不是把推送灌进聊天流——本设计沿用"可扫读条目"思路，但载体以对话与轻量提示为主（见 2.3）；
3. **必须带"为什么"**——"通知只是告诉你'有件事'，提醒才是告诉你'这件事为什么重要、什么时候处理'"（这句来自国内 OA 产品的实践总结，与本设计的证据链要求高度一致）；
4. **反馈闭环是标配**——Pulse 的点赞/点踩/curate 就是在让用户塑造内容；
5. **用户控制权是硬需求**——Copilot 有数量上限、飞书标注"授权范围内"、Pulse 可整体关闭。

本模块相对市面产品的**差异化优势**：本平台的业务数据是结构化的（合同、任务、审批都在表里），所以"发现"和"证据链"可以做到 SQL 级硬证据（哪条记录、哪个字段、什么时间读的）。

## 2. 关键设计决策（每条：决策 + 为什么 + 否决了什么）

### 2.1 决策一：发现用规则，表达用 AI

**决策：** "发现该管的事"由确定性代码/SQL/规则完成；LLM 只负责"把已经确定的事实说成人话"。

**为什么：**

- 快、准、免费、可复现、可审核——规则命中就是命中，工程师和业务能一起核对；
- 让 LLM 扫描数据"发现"问题，会贵、会慢、会不稳定、无法追溯（"为什么昨天报了今天没报"无法回答）；
- 提醒一旦出错，用户对整个管家的信任就崩了。发现层的确定性是信任的根基。

**否决了什么：**

- 否决"LLM 定期通读业务数据找异常"：成本不可控（每次全库扫描的 token 消耗巨大）、结果不可复现（同一数据两次扫描结论可能不同）、无法向业务解释漏报误报。
- 否决"纯人工配置的 BPM 告警"：那是传统 OA 的做法，表达僵硬、不会说人话、无法对话处理，与本产品"会说话、能对话"的定位相悖。

**边界：** 第一期只做"硬规则 + 状态机规则"两类（见 5.1）；"统计对比"作为第二层按需接入（快照基础已有）；"语义判断"（LLM 读合同条款找风险）最后做，且只做辅助提示，不单独产出跟进事项。

### 2.2 决策二：LLM 只做翻译官，输出必须过引用校验

**决策：** LLM 在链路中的唯一职责是"翻译"——把规则产出的结构化证据素材写成用户能读懂的标题与说明；输出结果必须通过引用校验（文案中的事实必须能在素材里找到对应），校验不过就降级为模板文案。

**为什么：**

- 需求要点：AI 送出提醒时必须带上作出判断的依据与证据链。证据链的可信度必须锚定在确定性代码上：**证据由代码收集，AI 不得自行添加事实**；
- 借鉴知识库 RAG 的引用校验模式（引用必须能在来源中找到），这是项目里已经验证过的手段；
- 成本可控：翻译是一次小的模型调用，比"让模型分析整个业务库"便宜几个量级；失败还能降级为模板文案，功能不中断。

**证据链的组成**（详见 5.2）：结论 + 结构化依据清单（事实、来源、读取时间）+ 命中的规则与阈值。它有两个用途：① 展示"为什么"给用户；② 用户点进对话处理时，整条事项 + 证据作为对话上下文注入——AI 已经知道催什么、为什么、找谁。

### 2.3 决策三：跟进记录 = 管家的工作笔记本（独立数据面）

**决策：** 新建独立的"跟进记录"数据面，记录"管家在替谁跟什么事、跟到哪一步了"（信息载体与职责见第 4 章，表结构见技术设计）。它是管家的记忆载体，**不是产品形态**——产品形态是"AI 主动说话 + 用户一句话处理"。

**为什么需要独立数据（而不是复用通知中心）：**

| | 通知中心（现有） | 跟进记录（新） |
| --- | --- | --- |
| 回答的问题 | "我告诉你有这事" | "这事的处理状态是什么" |
| 生命周期 | 读了就完（readAt） | **必须闭环**：待处理 → 已处理/用户弃管/自动恢复/过期 |
| 核心字段 | 标题+正文+读状态 | 业务对象 + 证据链 + 状态流转 + 处理结果 + 反馈 |
| 谁生产 | 系统/固定规则 | 规则发现 + AI 翻译 |

语义、生命周期、字段都不同，硬塞进通知表会让两边都变形。**通知中心降级为"送达渠道之一"**（事项送达时写一条通知，让"铃"响起来），不再是内容载体。

**为什么不做在对话流里（不塞进聊天）：**

1. 一个承载"所有跟进"的常驻会话会无限膨胀，天天触发压缩，成本和噪声都高（跟进记录不是聊天史，也不需要上下文压缩——它用状态机治理生命周期）；
2. 对话天生不适合做状态管理——翻聊天记录看不出"哪件事还没处理"；
3. 与"事找人"的目标错配：用户需要的是"AI 来说 + 我一句话回"，而不是"我去翻一个对话流"。

**为什么这不是"看板/待办"：** 数据模型和查询能力是"管家的笔记本"（它自己要记住在跟哪些事），属于实现手段。对用户的呈现形态见 2.4——轻提示引起注意、卡片视图可扫读、处理回到对话；它是"被提醒后看一眼"的落点，绝不新做"要用户定期巡查的页面"。

**否决了什么：**

- 否决"改造 notifications 表加状态机"：会同时污染通知（轻量、只读、可群发）和跟进（重、要闭环、单人）两种语义，通知中心的现有使用方（日报提醒、合同到期、系统公告）也会被牵连；
- 否决"每个用户一个常驻管家会话"：见上面第 1、2 条原因。

### 2.4 决策四：呈现形态——卡片式跟进视图，挂在唯一的 AI 入口下

**决策：** 跟进事项对用户分三层呈现：

| 层 | 形态 | 说明 |
| --- | --- | --- |
| 引起注意（送达） | 轻提示 | AI 入口角标 + 一条站内通知（复用通知中心）；不弹窗、不打断 |
| 可扫读一览（查看） | 卡片 | "跟进视图"（AI 交互界面内的一个视图切换）：按级别/域排序，卡片含标题、为什么（证据摘要）、级别、时间与操作按钮 |
| 处理（闭环） | 对话 | 点卡片带着事项与证据进入对话，AI 接着说细节；"处理完了/不用管/让 AI 去办"都在这里完成 |

**为什么是卡片，不是聊天气泡：** 气泡是聊天史的形态——时间序、无状态、只增不减，"哪件事还没处理"在气泡里没有载体（2.3）。跟进事项是状态序：需要扫读、排序、原地处理与关闭——这是卡片的形状（同类场景主流产品均为可扫读卡片，见 1.6）。两者不矛盾："扫读用卡片、处理用气泡"。

**为什么不是独立入口：** 守住"一个 AI 原则"（1.3）——管家不建独立页面、独立标签或独立会话；跟进视图挂在 AI 交互界面内的一个视图切换上，用户找管家永远只有一个固定位置。它是"被提醒后看一眼"的落点，不是需要定期巡查的页面（2.3）。

**视图模板可配置（结构第一期就留好）：** 不同岗位的侧重点不同，呈现随配置走，与发现层的组装思想（5.1）对称：

- **卡片组件（代码）**：渲染逻辑写一次——标题、为什么（证据摘要）、级别、时间、操作按钮；
- **视图模板（配置）**：显示哪些域、卡片显示哪些字段、排序、密度、可用操作；
- **岗位组装（配置）**：财务模板 = FINANCE + COMMON 域；法务模板 = LEGAL 域、含合同方字段。

第一期平台一套默认模板（渲染由配置驱动，结构上支持多模板）；演进方向：岗位模板实例化、租户在平台预置模板间选择。**不做**面向终端用户的页面搭建器——与"不做规则编辑器"（2.9）同一纪律：呈现是产品能力，不是客户 DIY 工程。

**否决了什么：**

- 否决"把提醒做成消息中心里的一条条记录"：通知中心已降级为送达渠道（2.3），状态与闭环不在它那里；
- 否决"独立管家页面/导航入口"：违反一个 AI 原则（1.3），制造第二个要用户惦记的地方；
- 否决"聊天流内互动卡片（消息即待办）"：气泡无法承载状态管理，等于把 2.3 否决的"常驻会话清单"换个壳。

### 2.5 决策五：用户设置 > 推送策略 > 内容（三层制度）

**决策：** "推不推、推多少"由三层制度决定，用户意愿是第一层，代码强制执行：

```
第1层 · 用户提醒设置（硬约束）
    开关 / 每日条数上限 / 静默时段 / 按域订阅
    → 每次送达前必查，这层说"不"，谁也送不出去
第2层 · 推送策略（规则自带，软约束）
    同规则降频、时间窗抑制、严重级别分级
第3层 · 内容生成（LLM 参考个人记忆措辞）
    记忆里"这人讨厌被催" → 措辞温和、并入汇总
```

**为什么：** 推送服务必须服从用户意愿，否则就是骚扰——这条是市面共识（Copilot 给提醒设数量上限、飞书强调"授权范围内"、Pulse 可整体关闭）。这里需要明确一个设计立场：**不是"记忆 vs 推送谁优先"，而是"设置 > 推送，记忆是设置的输入源之一"**。用户对 AI 说"以后日报别催我了"——必须写进**提醒设置**（硬生效），可以顺带进记忆（作参考）；只写记忆不写设置，就是"说了也没用"，体验会崩。

### 2.6 决策六：行为史靠"查"不靠"记"

**决策：** AI 的行为历史（干过什么、跟过什么）不写入个人记忆；需要时通过结构化查询回答（后续给对话加一个"查询我相关的跟进/动作"的读工具）。

**为什么：**

- 个人记忆（30 条）的定位是"关于用户的长期属性"，事件流水会让它迅速污染成行为日志，记忆就废了；
- 行为历史已经在数据库里：工具调用、已执行动作流水、待确认草稿、审计日志、加上本模块的跟进记录——它们是结构化、可查询、实时的事实源；把它们再"记"一份到记忆等于造一个会过期、会漏、会矛盾的第二事实源；
- 跨会话的"事务连续性"（"上次那事跟到哪了"）靠状态表回答：草稿表、跟进记录表本身就是跨会话状态，不需要记忆来扛。

**关于"要不要定期维护记忆"：** 不需要。有一个容易参照错的对象：飞书智能伙伴会"每天自动从工作内容中提炼记忆"——那是因为它的工作数据在文档和聊天里（非结构化），不提炼就丢了；本平台的业务数据在数据库表里，AI 直接查表比"提炼成记忆"更准、更新、更便宜。**数据形态不同，策略不同，不是飞书错了，而是不能照抄。**

**什么会写记忆：** 只有明确的长期偏好（且优先写入结构化"提醒设置"，记忆作补充）。忽略一条提醒、读过一条记录，都不进记忆。

### 2.7 决策七：反馈闭环——用户反馈塑造管家的行为

**决策：** 用户对每条跟进的主要动作（处理完 / 不用管 / 长期屏蔽这类提醒）都是反馈信号，系统据此调整该用户的推送策略：忽略 → 该规则对该用户降频；"不用管" → 短期抑制同类；"屏蔽" → 写入该用户的设置（或生成为一条待确认的设置建议）。

**为什么：**

- Pulse 的点赞/点踩/curate 证明"反馈塑造"是主动式产品的核心机制——没有反馈，管家永远学不会分寸；
- 没有反馈闭环，"防打扰"就只能靠拍脑袋的全局参数；有反馈，分寸就是每个用户自己教出来的；
- 该能力属于主动式产品的通行机制，在本设计初稿中曾经遗漏，经市面调研确认后纳入第一期范围（块 5）。

### 2.8 决策八：防打扰——告警饱和是头号敌人

**决策：** 送达前有四道闸门（详见 5.3）：同一件事幂等去重、同规则对同用户时间窗降频、用户每日上限（超出合并为一条摘要）、静默时段（可被 CRITICAL 级别穿透，由用户设置）。宁可少推，不可滥推。

**为什么：** 安全运营行业对"告警饱和"有明确共识——推送多了等于没有推送，还赔上信任。**错推比不推伤害大**：漏推是功能问题，误推是信任问题。这条直接约束规则准入标准：第一条规则必须"准到可以人工复核通过"才允许上线。

### 2.9 明确不做的清单（汇总）

| 不做 | 原因 | 何时重新考虑 |
| --- | --- | --- |
| LLM 自主扫描发现（第一期） | 贵、慢、不可复现、难审核（2.1） | 语义类判断作为辅助层时局部引入 |
| 把主动消息直接写进对话流（送达形态） | 需改造会话发起模型、会话级实时事件与两端未读体系；且"提醒灌进聊天流"在主流产品中均非首选形态（1.6）。不做它不影响"一个 AI 原则"——管家本就是同一个 AI 的主动模式（1.3），处理动作始终回到对话 | 用户明确需要"对话内管家频道"体验时，作为二期评估 |
| 把跟进/忽略写进个人记忆 | 污染记忆（2.6） | 不 |
| 独立看板页面、报表、导出 | 定位红线（1.3） | 不 |
| 面向租户的规则编辑器 | 定位红线（1.3） | 出现明确的"租户自定义阈值"需求时，做最小参数覆盖 |
| 跨用户的"催办/代办"协作 | 属"跨人协作"模块（委托与授权），本模块只做"发现→送达→闭环"，处理动作复用现有工具+确认机制 | 跨人协作模块立项时 |

## 3. 总体架构：管家跟进五段链路

### 3.1 链路总图

```
① 发现            ② 抑制聚合          ③ 翻译表达           ④ 落库送达           ⑤ 反馈与闭环
┌──────────┐     ┌──────────┐      ┌──────────┐       ┌──────────┐       ┌──────────┐
│ 定时扫描  │     │ 幂等去重  │      │ LLM 翻译  │       │ 写入跟进  │       │ 用户动作  │
│ 业务事件  │ ──▶ │ 时间窗降频│ ──▶  │ 引用校验  │ ──▶   │ 记录表    │ ──▶   │ 处理/弃管 │
│ 对话顺带  │     │ 每日上限  │      │ 失败降级  │       │ 通知铃    │       │ 反馈调参  │
│ (规则SQL) │     │ 静默时段  │      │ 模板兜底  │       │ 查询接口  │       │ 自动复核  │
└──────────┘     └──────────┘      └──────────┘       └──────────┘       └──────────┘
   确定性            确定性              AI 唯一介入点         确定性             确定性 + 学习
```

**一个总原则：AI（LLM）只出现在第 ③ 格。**发现、抑制、落库、送达、闭环全部是确定性代码。这个分界保证：提醒为什么出现、为什么没出现，永远可以回答。

### 3.2 各段职责与边界

| 段 | 职责 | 明确不做 |
| --- | --- | --- |
| ① 发现 | 按规则扫描业务数据，产出"命中事实包"（对象 + 证据字段 + 命中的规则） | 不做优先级判断（那是 ②）、不生成文案（那是 ③） |
| ② 抑制聚合 | 去重、降频、上限、静默、级别过滤、合并摘要 | 不做业务判断，只看"该不该此刻送" |
| ③ 翻译表达 | 事实包 → 标题 + 人话说明 + 引用编号；过引用校验 | 不添加素材外的事实；不决定推给谁 |
| ④ 落库送达 | 写跟进记录（幂等）+ 写通知（铃）+ 提供查询/处理能力 | 不做实时推送基建（沿用现有轮询/通知机制） |
| ⑤ 反馈闭环 | 用户动作落库 → 调整该用户策略 → 下轮扫描自动复核已恢复的条目 | 不自动"假装用户处理了"；不写记忆流水 |

### 3.3 触发机制：定时为主，事件为辅，对话顺带

| 触发方式 | 适用 | 第一期 | 理由 |
| --- | --- | --- | --- |
| **定时扫描** | 状态类问题：合同到期/停滞、任务逾期、审批堵塞 | ✅ 主力 | 复用后台任务框架（60 秒轮询 + 分布式锁），零业务代码侵入，可补算可复现 |
| **业务事件触发** | 即时类：被拒绝、被撤回、金额超阈值 | ⏳ 第二期按场景补 | 现有业务模块已有"业务事务内投递通知"的模式可循，不需要引入消息队列；但逐点埋钩子侵入大，只给真正需要实时的场景做 |
| **对话顺带检查** | 用户进对话时提示"你有 N 件在跟进" | ⏳ 块 6 小改 | 提高曝光又不打扰：在对话开场注入跟进摘要（"进对话时拉取"，不是"往对话塞消息"） |

### 3.4 与现有系统的复用关系（什么都不重造）

| 现有能力 | 在本模块的角色 |
| --- | --- |
| 后台任务框架（`apps/api/src/jobs`） | 承载定时扫描（新增一类扫描任务） |
| 通知中心 | 送达渠道之一：事项送达时写通知，让铃响 |
| 用户级记忆 | 第 ③ 步生成时的参考输入（措辞分寸） |
| 上下文压缩 / 会话机制 | 不受影响：本模块不产生新对话流、不写聊天记录；用户在对话中处理跟进事项时，走的仍是现有会话与压缩机制 |
| RBAC + 数据范围（`DataScopeResolverService` 等） | 决定"该发现谁的事、该送给谁"——含红线校验 |
| 工具 + 待确认草稿机制 | 用户处理跟进时的执行通道（"让 AI 去办"复用现有工具链） |
| ai-service 网关与模型路由 | 第 ③ 步翻译调用（新增一个内部接口） |
| 指标快照 / 现有异常规则 | 第二层"统计对比"判断的数据基础；8 条首页规则是"发现"规则的现成候选池 |
| 审计体系 | 跟进记录的创建/送达/处理动作全程可审计 |

## 4. 信息与数据（设计层）

> 本章描述"管家需要记住什么、各自承担什么职责"；字段、迁移与幂等实现属于施工图，见配套[技术设计](../architecture/proactive-assistant-technical.md)，实施时以 Prisma 迁移为准。

### 4.1 三类信息载体

| 载体 | 回答什么 | 职责 |
| --- | --- | --- |
| 跟进记录 | 管家在替谁跟什么事、跟到哪一步 | 本模块的核心数据：业务对象、证据链、状态流转、处理结果与反馈；用户处理动作的落点 |
| 规则配置 | 哪些事该管、阈值多少 | 每条规则的开关、职能域、严重级别、阈值参数、扫描节奏；"逻辑在代码、参数在表"（见 5.1） |
| 提醒设置 | 这个人愿意被怎么提醒 | 个人级的开关、每日上限、静默时段、按域订阅；送达前的硬约束（2.5） |

规则配置的设计取舍：让使用者直接写条件表达式会造出一个迷你规则引擎——超出第一期需要，且错误配置会直接产生错误提醒，风险不可控。因此采用"逻辑在代码、参数在表"：调整阈值、停用规则是运营动作；新增规则是开发动作（一条检测逻辑 + 一行配置）。租户级阈值覆盖列为未来扩展点，第一期不做。

### 4.2 状态与生命周期

一条跟进从被规则命中开始，到用户处理、自行恢复或超期结束：

```
                     ┌──────────────┐
  规则命中 ────────▶ │   PENDING    │  （管家在跟进；可能未送达——静默期）
                     └──────┬───────┘
          用户"处理完了" ────▶ RESOLVED (MANUAL)
          用户"不用管"   ────▶ DISMISSED（短期抑制同类）
          下一轮复核不命中 ──▶ RESOLVED (RECOVERED)  ← 事情自愈（如合同已续签）
          超期未处理      ────▶ EXPIRED（默认 30 天，规则可覆盖）
```

关键点：

- **自动复核（RECOVERED）**：每轮扫描先复查仍在跟进的记录，业务条件不再命中 → 自动关闭并标注"已自行解决"。这防止"事早办完了管家还在催"——Pulse 曾因推送已完成事项而受到用户批评，该机制在源头避免同类问题；
- 所有状态流转写审计；用户操作（处理完成/不用管）幂等：重复请求返回当前状态，不报错、不双写。

### 4.3 幂等与去重（原则）

- 同一件事对同一个人只创建一条跟进记录：重复命中只刷新证据与时间，不新建、不重复送达；
- "时间窗降频"改变的是"送不送"，不是"记不记"——记录一直在（管家始终记着），送不送由抑制层决定（5.3）；
- 幂等键设计与通知防重复用细节见技术设计。

## 5. 核心机制

### 5.1 规则体系：发现什么算问题

**第一期只做前两层，第三层按需，第四层最后：**

| 层 | 判断方式 | 例子 | 落地 |
| --- | --- | --- | --- |
| 硬规则 | 阈值/期限/停滞，纯 SQL | 合同到期前 N 天、超期未审批、X 天无更新 | ✅ 第一期 |
| 状态机规则 | 卡在节点/该走的没走 | 合同已签未归档、入职未建账号 | ✅ 第一期备选 |
| 统计对比 | 与自身历史/均值对比 | 费用环比异动、工作量骤降 | ⏳ 快照基础已有，按需 |
| 语义判断 | LLM 读内容找风险 | 条款风险、沟通异动 | ⏳ 最后做，仅辅助提示 |

**规则准入标准（防打扰的制度化）：** 每条新规则上线前必须通过三项人工复核——① 命中样本逐条人工确认"确实是该管的事"；② 误报率可接受（首批规则要求接近零误报）；③ 证据字段齐全（能写清楚"为什么"）。做不到就不上——**规则入库的门槛就是"准"**。

**不同岗位/职能域的差异**（发现能力怎样覆盖不同岗位）：差异不在技术而在业务知识——每个岗位的"什么算问题"是业务定义。差异化体现在三个维度：

- **规则集不同**：财务看资金待付积压，人事看简历池与异动，法务看合同停滞；
- **数据范围不同**：同一条规则对谁生效，复用实时数据范围解析（只能用收件人权限内的数据算）；
- **阈值不同**：同一检测逻辑在不同场景使用不同参数（合同停滞 14 天、任务停滞 7 天）。

落地思路上，这套差异由"检测逻辑（代码）× 规则实例（配置）× 域组装（配置）"三层装配完成：一条检测逻辑只写一次、可被多条配置实例复用（不同对象、不同阈值）；每个职能域挑选自己的规则集。未来给某岗位"加发现能力"= 复用现有检测逻辑只加配置行（运营动作），或写一条新检测逻辑 + 配置行（开发动作）。框架细节见技术设计。这套"什么算问题"的业务知识沉淀，就是产品的长期壁垒。

### 5.2 证据链

**原则：证据在第 ① 步（发现）就结构化收集完毕，第 ③ 步只做翻译。** 证据链由四部分组成：

- **结论**：规则判定的一句话（如"合同 A 疑似停滞"）；
- **依据清单**：一组结构化事实（字段名、显示名、取值、来源字段），每条可回溯到具体表字段；
- **规则与阈值**：命中的规则编码、阈值参数、严重级别；
- **读取时间**：证据是"当时读到的事实"，用户事后质疑时能解释。

三条纪律：

1. 依据是结构化字段，不是自然语言段落——来源可复核、可被引用校验；
2. 不存放自由文本大段原文（如合同全文），防止敏感长文本被复制进推送数据；需要细节时凭业务对象去原页面查看（权限控制仍在业务侧）；
3. AI 只能翻译、不得添加素材外的事实（见 5.4）。

数据结构与示例见技术设计。

### 5.3 抑制聚合：四道闸门

送达前按顺序过四道闸门（全部确定性代码）：

| 闸门 | 规则 | 效果 |
| --- | --- | --- |
| ① 幂等去重 | dedupKey 唯一 | 同一件事对同一人只送一次；重复命中只更新证据 |
| ② 时间窗降频 | 同规则对该用户 N 小时内最多 1 次（规则表参数） | 防止同类问题刷屏（如 5 份合同同时到期 → 汇总为一条） |
| ③ 每日上限 | 提醒设置的每日上限（默认 10） | 超出部分不丢弃、延迟到次日合并摘要送达 |
| ④ 静默时段 | 提醒设置的静默时段 | 静默期内发现的事项标记"待送达"，出静默期统一送（CRITICAL 可按用户设置穿透） |

**聚合原则：** 同一批次同一对象的多个规则命中，合并为一条（选最高 severity）；同一规则的多个对象命中，可合并为"3 份合同即将到期"的摘要条目（块 4 实现，先做基础合并）。

### 5.4 AI 翻译与引用校验

**设计要点：** 翻译素材 = 规则信息 + 证据依据 + 收件人背景（含记忆中的措辞偏好）。AI 输出标题、说明与引用编号，必须通过引用校验（文案中的事实能在素材中找到对应）才被采用；校验不通过或调用失败，降级为规则模板文案，功能不中断。调用链与降级实现见技术设计。

**提示词纪律（写入 ai-service 侧约束）：**

- 只能用素材里给定的事实，不得添加、推断素材外信息；
- 文案结构固定：说清"什么事 + 为什么找到你 + 建议下一步"；
- 不输出内部 ID、权限枚举、主机名等内部标识（沿用现有脱敏规范）；
- 文案面向用户可见，素材选取阶段就按"收件人权限内数据"裁剪。

**成本控制：** 翻译走便宜模型档位；单租户每日翻译调用设上限（超出部分当日降级模板文案）；调用计量纳入现有 AI Credit 体系。

### 5.5 送达与响应

**送达（块 3）：**

- 事项送达时写一条站内通知（复用通知中心，接收人 = 收件成员，带跳转）——让"铃"响起来，通知是送达渠道，不是内容载体；
- 提供"我的跟进"查询能力（细节见技术设计），支撑客户端在用户主动查看时呈现；
- 对话内查询：给对话加一个读工具（`list_follow_ups`），用户可直接问 AI"最近有什么事要我处理"，AI 查表回答——呈现以对话优先，不依赖新页面。

**响应（两条路，都走现有能力）：**

| 用户动作 | 系统行为 |
| --- | --- |
| "处理完了"（手动标记） | 状态 → 已处理（手动），记录处理时间与操作者 |
| "不用管" | 状态 → 弃管，并作为反馈信号进入闭环 |
| "让 AI 去办"（如"帮我催一下"/"去确认"） | **不在本模块**——跳转现有对话，携带该跟进事项与证据作为上下文，AI 用现有工具链与待确认草稿机制执行；执行完成回写该跟进的关联动作 |
| 什么都不做 | 保持跟进中，按策略推动（时间窗降频；"升级找人"属跨人协作方向，本期不做，见 2.9） |

### 5.6 反馈闭环（块 5）

- **数据**：每次用户动作（查看/处理/不用管/屏蔽）写入该记录的反馈信息；
- **短期**：弃管（DISMISSED）后，同类消息在该用户处短期抑制（如 7 天）；
- **长期**：同一规则被同一用户连续弃管/屏蔽达阈值 → 自动关闭该规则对该用户的推送，并生成一条设置建议（"你已多次跳过 X 类提醒，是否停用？"）——用户确认后写入该用户的提醒设置；
- **重要**：反馈调整的是"设置与策略层"，**不修改规则本身的业务判断**——规则对所有人的业务正确性不由个体反馈决定。

## 6. 权限与安全红线

- **红线一（最重要）**：给 A 的提醒，只能用 A 权限内的数据算出来。发现阶段就按收件人的数据范围过滤（复用现有数据范围解析）；**绝不允许**把 B 部门的数据算进 A 的提醒——主动推送的越权事故比对话内越权严重得多；
- **红线二**：任何展示该数据的入口实时二次校验（生成时有权、查看时被回收 → 不可见）；成员停用、删除或租户停用 → 不可见（沿用现有成员状态校验）；
- **红线三**：审计不落证据全文与敏感参数（沿用现行动作审计的字段白名单惯例）；
- **权限接入**：新增一个"查看与处理自己的跟进"权限码，随迁移授予已有默认角色（做法与工作台权限 `dashboard.read` 相同）；契约版本与客户端生成细节见技术设计。

## 7. 分块实施计划

> 遵循项目"分块渐进"纪律：每块独立可验证、独立提交；每块完成后停下评审再进下一块。

| 块 | 内容 | 验收口径 |
| --- | --- | --- |
| **块 1** | 数据模型与迁移（3 张表）+ 规则框架 + 第一条规则（建议：合同到期/停滞，复用现有到期提醒逻辑迁移）；产出跟进记录（文案先用模板） | 迁移通过；跑一轮扫描能在表里得到正确记录；自动复核逻辑单测通过 |
| **块 2** | AI 翻译（ai-service 内部接口 + NestJS 素材组装 + 引用校验 + 降级） | 单测：素材→文案→校验；引用不合法时降级模板；真实素材人工抽查 20 条 |
| **块 3** | 送达与查询能力（通知送达 + 跟进查询/处理能力 + 权限码 + 契约与客户端重新生成） | 契约校验与生成通过；鉴权/越权/幂等/二次校验单测；通知可送达 |
| **块 4** | 设置与抑制聚合（四道闸门 + 设置接口/页面数据支持） | 闸门逐条单测：重复、降频、上限、静默/穿透；设置变更即时生效 |
| **块 5** | 反馈闭环（弃管抑制、屏蔽→设置建议） | 反馈信号落地并可查询；降频/停用行为可验证 |
| **块 6** | 扩展：第二条规则（覆盖另一职能域）+ 对话读工具 `list_follow_ups`（"最近有什么事"）+ 对话开场摘要注入评估 | 多域规则并行扫描互不干扰；对话中可查询并正确引用证据 |

遵循项目工程规范：每块独立验证、独立提交，功能整体完成后统一提一个 PR。

## 8. 风险与边界

| # | 风险 | 控制措施 |
| --- | --- | --- |
| 1 | **越权推送**（把不该给某人看的数据算进提醒） | 发现阶段按收件人数据范围过滤 + 查询阶段二次校验；专项测试覆盖 |
| 2 | **误报伤信任**（错推比不推伤害大） | 规则准入三项人工复核；首批规则要求接近零误报；自动复核机制防"事完了还催" |
| 3 | **告警饱和** | 四道闸门 + 反馈闭环；每日上限默认 10；宁可延迟合并不可滥推 |
| 4 | **AI 文案幻觉** | 只翻译不判断；引用校验不通过即降级模板；脱敏规范沿用现有约束 |
| 5 | **成本失控** | 翻译用便宜档位 + 每日调用上限 + 失败降级；计量入 AI Credit 体系 |
| 6 | **静默/时区错误** | 静默时段按租户时区（`tenants.timezone`，缺省 Asia/Shanghai，沿用工作台的时区规则） |
| 7 | **隐私** | 证据只存字段级摘要与来源，不复制敏感长文本；审计字段白名单 |
| 8 | **权限快照过期** | 不做权限快照：生成与查询都用实时解析（与工具执行的既有纪律一致） |
| 9 | **范围蔓延** | 第 1.3、2.9 两节是范围红线：任何新增需求先对照"明确不做的清单" |
